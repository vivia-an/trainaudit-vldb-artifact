# 复现经验与论文素材

> 基于 M-005 和 M-010 的完整复现过程，分两类记录：技巧（加速后续复现）和本质困难（写进论文）。

---

## 一、技巧：加速后续 bug 复现

### 技巧 1：用 `run_with_trace.py` 模板而非通用 wrapper

**经验**：试了 3 种注入 trace 的方式，最终成功的是最简单的：

```python
# run_with_trace.py（3 行核心逻辑）
import megatron.training.training as mtt   # 先 import megatron（让模块加载）
mtt.train_step = _patched_train_step       # 直接替换 train_step
exec(open("pretrain_gpt.py").read())       # 执行 Megatron 原版入口
```

失败的方式：
- ❌ `inject_trace.py` 调用 `pretrain()` → 不同版本签名不同
- ❌ `sitecustomize.py` import hook → exec 中不触发
- ❌ 通用 wrapper 替换 pretrain 入口 → API 不兼容

**模板在 `benchmark/run_with_trace_template.py`，每个 bug 复制一份即可。**

### 技巧 2：确认 commit 是否正确

**经验**：M-001 花了很长时间调试，最后发现 commit 找错了。

**必做步骤**：
```bash
git diff {buggy_commit} {fixed_commit} -- '*.py'
```
快速扫 diff 内容，确认和 issue 描述的 bug 一致。如果 diff 改的是无关代码 → commit 错了。

### 技巧 3：用 `--mock-data` 而非假预处理数据

**经验**：假预处理数据（.bin + .idx）的格式跨版本不兼容（header 8 bytes vs 9 bytes，字段校验不同）。

**规则**：
- 优先用 `--mock-data`（大部分 2024 年后的 commit 支持）
- 不支持的旧版本再用假数据
- 用 `grep "mock" megatron/*/arguments.py` 快速判断

### 技巧 4：BF16 而非 FP16

**经验**：FP16 + mock data 容易 NaN overflow → loss scale 持续下降 → 训练行为被 loss scaling 机制掩盖。

**规则**：默认用 `--bf16`，除非 bug 本身依赖 FP16 的 loss scaling 机制。

### 技巧 5：`CUDA_DEVICE_MAX_CONNECTIONS=1` 必须设

**经验**：Megatron 的 async gradient all-reduce 需要这个环境变量，不设会直接报错退出。

### 技巧 6：`tools/__init__.py` 必须创建

**经验**：旧版 Megatron 的 `tools/retro/` 不是 Python 包，`from tools.retro.utils import ...` 会失败。

**在 checkout 后立即执行**：
```bash
[ -d tools ] && [ ! -f tools/__init__.py ] && touch tools/__init__.py
[ -d tools/retro ] && [ ! -f tools/retro/__init__.py ] && touch tools/retro/__init__.py
```

### 技巧 7：`tensor_hash` 必须处理 BF16

**经验**：`.numpy()` 不支持 BFloat16，必须先 `.float()`。

```python
data = t.detach().contiguous().cpu().float().numpy().tobytes()
```

### 技巧 8：端口冲突

**经验**：多次跑 torchrun 会端口冲突。

**规则**：用 `--master_port=${MASTER_PORT:-29501}` 允许覆盖，或每次跑前 `pkill -f torchrun`。

## 二、本质困难：写进论文的素材

### 困难 1：通用 trace diff 无法检测所有 silent error

**证据**：M-010 的 buggy 和 fixed 版本在 20 步训练后的 trace（参数 cksum、loss、grad_norm）**完全一样**。

**原因**：M-010 的 bug 是 aux_loss 被累加两次，但 aux_loss 的影响太小（相对于 lm_loss），在短期训练内不改变参数的 bit-exact 值。

**论文论点**：基于 trace diff 的检测（包括 TrainCheck 的 pattern matching）无法检测这类 bug。需要针对 bug 语义定义 invariant（"aux_loss 每步每层应该被保存 1 次"），然后 hook 对应的函数检查。

**对比数据**：
| 方法 | M-005 | M-010 |
|------|-------|-------|
| trace diff（cksum 比较） | ✅ 426 diffs | ❌ 0 diffs |
| semantic invariant | ✅ router.weight 跨 TP rank 不一致 | ✅ aux_loss 调用 2x |

### 困难 2：每个 bug 需要不同的 invariant

**证据**：M-005 用的是 "cross-rank cksum equality"，M-010 用的是 "函数调用次数检查"。没有一个通用 invariant 能同时检测两者。

**论文论点**：invariant 必须从 bug 的语义中推导。这要求理解：
- M-005：理解 "TP 下 router weight 应该在所有 rank 上一致"
- M-010：理解 "activation checkpointing 的 no_grad forward 不应该累加 aux_loss"

这些知识来自框架源码和设计文档，不来自 trace 数据。

### 困难 3：bug 的触发条件散落在代码中

**证据**：

| Bug | Issue 描述的条件 | 实际需要的额外条件 | 怎么发现的 |
|-----|-----------------|-------------------|-----------|
| M-005 | TP > 1 + SwitchMLP | + GPU 初始化（非 CPU） | 跑了才发现 CPU init 下不触发 |
| M-010 | activation checkpointing | + `--moe-layer-recompute`（不是通用 recompute） + `--moe-aux-loss-coeff > 0`（默认是 0） | 读源码发现用的是 MoE 专用 recompute，且 aux_loss 系数默认关闭 |

**论文论点**：bug 的 precondition 不完整是常态。Issue 描述只给出必要条件的子集，真正的触发条件需要深入源码分析执行路径。这是 LLM 从源码提取 precondition 的价值所在。

### 困难 4：同一个检测工具在不同 bug 上的角色不同

**证据**：
- M-005：sdctrace 采集 cksum → trace_diff.py 对比 → 检测成功
- M-010：sdctrace 采集 cksum → trace_diff.py 对比 → **检测失败**。需要另写 `detect_m010.py` hook `save_to_aux_losses_tracker`

**论文论点**：没有 one-size-fits-all 的检测工具。需要一个框架来：
1. 根据 bug 类型选择检测策略（cross-rank 比较 / 函数调用计数 / 值范围检查 / ...）
2. 根据 bug 语义生成对应的 hook 和 invariant
3. LLM 在这个过程中的作用是：读懂 bug → 选择策略 → 生成检测代码

### 困难 5：跨版本 API 不兼容使批量化不可能

**证据**：32 个 Megatron bug 跨越 2+ 年：
- `pretrain()` 签名至少有 3 种不同版本
- `train_step()` 在 `megatron/training.py` 或 `megatron/training/training.py`
- `model_provider()` 有的需要 `model_builder` 参数
- 数据格式：有的支持 `--mock-data`，有的不支持
- idx 文件格式：header 长度不同

**论文论点**：写一个通用的复现工具几乎不可能。每个 bug 需要独立的、针对那个版本的脚本。这也意味着 benchmark 的构建成本很高——这本身就是为什么之前没有人做过大规模 silent error benchmark 的原因。

### 困难 6：mock-data 跨版本不兼容

**证据**：M-020 的 buggy commit 的 `pretrain_gpt.py` 在 `--mock-data` 模式下仍然调用 `get_blend_and_blend_per_split(args)`，要求提供 `--data-path`，但 `--mock-data` 和 `--data-path` 互斥。

**解法**：monkey-patch `get_blend_and_blend_per_split` 在 mock 模式下返回 `(None, None)`。

**论文论点**：即使是 Megatron 自身的测试基础设施（`--mock-data`）在不同 commit 也有兼容性问题。复现 bug 不仅需要理解 bug 本身，还需要处理该版本的环境适配。

**这个对比表本身就是论文的一个核心表格**——展示了不同类型的 silent error 需要不同层次的检测能力。三种检测范式：
1. **数据对比型**（M-005）：比较不同 rank/版本的 trace 数据
2. **行为审计型**（M-010）：检查运行时函数调用是否符合预期
3. **结构校验型**（M-020）：验证模型结构与配置的一致性

## 四、复现失败的案例（同样有论文价值）

### M-021：Expert 参数未用分布式优化器更新

**Issue**: https://github.com/NVIDIA/Megatron-LM/issues/565

**Bug 描述**：expert 参数的梯度不在 GradBuffer 中，distributed optimizer 对 expert 参数退化为非分布式优化器，梯度不在 expert DP group 内 all-reduce。

**复现结果**：buggy 和 fixed 版本的 expert 参数 hash 完全一致（4 步训练后 bit-for-bit 相同）。

**原因分析**：Megatron 的 EP 实现中，同一 expert DP subgroup 的 rank 处理**相同的数据**（data modulo expert parallel），所以即使没有梯度 all-reduce，每个 rank 计算出的梯度天然一致。bug 的实际影响是**内存效率**（expert 参数无法享受 ZeRO sharding），而非训练正确性。

**论文论点**：并非所有标记为 "bug" 的 issue 都产生 silent error。有些 bug 只影响效率不影响正确性，需要深入理解并行策略的语义才能区分。

### M-008：overlap-param-gather 导致 loss 不下降

**Issue**: https://github.com/NVIDIA/Megatron-LM/issues/663

**Bug 描述**：DistributedOptimizer 的 `all_gather_handles` 列表每步 append 而不是覆盖，导致第二次非 skip 的 optimizer step 时 assertion 失败。

**复现结果**：
- `--initial-loss-scale 1`（不 overflow）：buggy 和 fixed 完全一致，bug 的 code path 不触发
- `--initial-loss-scale 4` 或默认（overflow）：两版都全部 skip，无法区分
- 根本问题：这是一个 **crash bug**（`assert 0 == N` 会直接报错），不是 silent error。只有在 FP16 永远 overflow（`update_successful=False`）时 assertion 被跳过，但此时 buggy 和 fixed 行为相同

**论文论点**：有些 bug 在特定数值条件下表现为 crash 而非 silent error。用假数据复现时，FP16 的数值行为（overflow/underflow）很难精确控制，这是假数据复现的根本局限。

### M-005：SwitchMLP router 权重跨 TP rank 不同步

**Issue**: https://github.com/NVIDIA/Megatron-LM/issues/599

**Bug 描述**：router 用 `torch.nn.Linear` 初始化，理论上不同 TP rank 的 CUDA RNG 不同会导致权重不一致。

**复现结果**：buggy 和 fixed 版本中，router weights 在 init time 和 train time 都跨 TP rank 完全一致。

**原因分析**：`torch.nn.Linear` 使用 default CUDA RNG，而 Megatron 在 `model_parallel_cuda_manual_seed` 中把 default CUDA RNG 设为 `data_parallel_seed`（所有 TP rank 相同）。只有 tensor-parallel RNG tracker 在不同 TP rank 上不同，但 `torch.nn.Linear` 不使用这个 tracker。因此 bug 的 code path 存在（用错了 init method），但在当前 RNG 配置下不产生可观测差异。

**论文论点**：bug 的可观测性依赖于运行时环境。同一个 bug 在不同 RNG 配置下可能是 silent error 也可能是无害的。这对自动化检测提出了挑战：不变量正确，但 bug 不触发。

### 困难 7：并非所有 bug 都能用假数据复现

**证据**：
| Bug | 假数据复现 | 原因 |
|-----|-----------|------|
| M-005 | ❌ | default CUDA RNG 恰好同步，cross-rank 差异不出现 |
| M-021 | ❌ | bug 只影响内存效率，不影响正确性 |
| M-008 | ❌ | bug 是 crash 而非 silent error；FP16 数值条件无法用假数据控制 |
| M-010 | ✅ | bug 在控制流，与数据无关 |
| M-020 | ✅ | bug 在配置校验，与数据无关 |
| M-024 | ✅ | bug 在 dtype，与数据无关 |
| M-012 | ✅ | bug 在 dtype，与数据无关 |

**成功复现的 bug 特征**：控制流错误、配置校验缺失、dtype 错误 — 这些不依赖数据内容或数值行为。

**失败的 bug 特征**：RNG 依赖、数值精度依赖、效率而非正确性 — 这些的可观测性取决于运行时环境。

**论文论点**：用假数据自动化构建 silent error benchmark 有天然边界。控制流/配置/dtype 类 bug 可以可靠复现（4/4 成功），而 RNG/数值类 bug 则不行（0/3 成功）。这不是方法的缺陷，而是 silent error 本身的复杂性。

# 复现问题回顾：哪些可以避免、哪些是本质困难

---

## 一、可以避免的问题（工程失误，下次做好就行）

### 1. BFloat16 的 numpy 不支持
- **现象**：`tensor_hash` 中 `.numpy()` 对 BF16 报 `TypeError: Got unsupported ScalarType BFloat16`
- **修复**：加 `.float()` 转换
- **教训**：写基础库时要覆盖所有 dtype，不能只测 FP32

### 2. FP16 随机数据 overflow
- **现象**：M-008 的 FP16 训练每步都 NaN → loss scale 持续下降 → LR=0，buggy/fixed 行为完全相同
- **修复**：用 `--initial-loss-scale 1` 或换 BF16
- **教训**：mock data + FP16 是有害组合，默认应该用 BF16

### 3. `tools/__init__.py` 缺失
- **现象**：旧版 Megatron 的 `tools/retro/` 不是 Python 包，import 失败
- **修复**：checkout 后自动 `touch tools/__init__.py`
- **教训**：跨版本脚本要处理包结构差异

### 4. `--mock-data` 不存在
- **现象**：旧版 Megatron 没有 `--mock-data` 参数
- **修复**：改用 DummyDataset + patch get_batch
- **教训**：不能假设所有版本有相同的 CLI 参数

### 5. optimizer hook 挂不上
- **现象**：`auto_trace` 的 `register_step_pre_hook` 在 Megatron distributed optimizer 上不生效
- **修复**：改为直接在 `patched_train_step` 里手动采集
- **教训**：框架的 optimizer 包装层会屏蔽 PyTorch 原生 hook

### 6. import path 跨版本不兼容
- **现象**：`from megatron import get_args` 在某些版本不存在
- **修复**：用 `inject_trace.py` 直接跑每个版本自己的 `pretrain_gpt.py`
- **教训**：不要写一个 wrapper 试图兼容所有版本，让每个版本用自己的代码

## 二、本质存在的困难（论文可以讨论的）

### 1. Bug 的触发条件是隐藏的

M-005 的 issue 说"TP > 1 时 router weight 不同步"。但真实复现发现 CPU 初始化路径下不触发——只有 GPU 初始化时才触发。

**这不是工程失误，是本质困难**：bug 的 precondition 散落在代码的执行路径中，不在 issue 描述里，不在 fix diff 里，甚至不在源码注释里。只有跑起来才能发现。

**论文价值**：这说明"从 issue 描述提取 precondition"是不够的，需要深入源码分析执行路径。LLM 在这方面有优势（能读完整个代码库）。

### 2. 同一个 invariant 在不同配置下是对/错

INV-001 检查"所有参数跨 TP rank 一致"。在 DP only 场景下完全正确。在 TP 场景下，大部分参数应该不同（TP shard），只有 router/norm 应该一致。

**这是本质困难**：不存在"普适的 invariant"。每条 invariant 的正确性取决于并行配置。一个 invariant 库必须是 topology-parameterized 的。

**论文价值**：这是 TrainCheck 等现有方法的核心局限——它们学到的 pattern 不区分"哪些参数在 TP 下应该相同"。这个区分需要 semantic knowledge。

### 3. buggy/fixed 版本在某些配置下 trace 完全相同

M-008 用 `--initial-loss-scale 1` 时，buggy 和 fixed 版本的 loss/LR/参数完全一样——bug 的触发路径被绕过了。

**这是本质困难**：不是所有 bug 都能在任意配置下触发。复现 bug 需要的不只是"正确的代码版本"，还需要"正确的运行时条件"。

**论文价值**：这说明纯 data-driven 的方法（从 healthy trace 学）在某些 bug 上会失效——因为 buggy trace 和 healthy trace 长得一模一样。检测这类 bug 需要理解"在什么条件下 bug 会触发"，这是 precondition knowledge。

### 4. 跨版本 API 不兼容

32 个 Megatron bug 跨越 2+ 年的版本。每个版本的 `pretrain()` 签名、`train_step()` 参数、model_provider 接口都可能不同。写一个通用 wrapper 几乎不可能。

**这是本质困难**：分布式训练框架演化快，检测工具必须适应不断变化的 API。

**论文价值**：这是 "trace 系统侵入性 vs 覆盖率" 的直接体现——零侵入的方法（PyTorch hook）不受 API 变化影响，但覆盖率低（20%）；高覆盖率需要侵入框架代码，而框架代码在不断变化。

### 5. mock data 不能完全替代真实数据

随机 token 产生的 loss landscape 和真实文本不同。某些 bug 只在特定数据分布下触发（如 masked mean 计算的 B14/B15）。

**这是本质困难**：小规模复现环境和生产训练环境之间存在 gap。

**论文价值**：这定义了 trace-based 方法的边界——sub-percent 数值偏差类的 bug 需要真实数据和长时间训练才能暴露。

## 三、如果解决了就是贡献的问题

### 贡献 1：Topology-aware parameter classification

**问题**：INV-001 不知道哪些参数在 TP 下应该一致、哪些应该不同 → 57 个 FP

**如果解决**：给定 Megatron 源码 + 并行配置，自动生成"每个参数在 TP/DP/PP 下的预期行为"（相同/不同/不存在）。

**怎么解决**：
- 让 LLM 分析 Megatron 的 `ColumnParallelLinear`、`RowParallelLinear`、`VocabParallelEmbedding` 等类，理解它们对参数的 shard 方式
- 输出：`{param_pattern: "*.router.weight", tp_behavior: "replicated", dp_behavior: "replicated"}`
- 将此知识编译成 invariant 的 precondition

**验证**：对比 LLM 生成的分类 vs 人工标注，计算 precision/recall

### 贡献 2：Bug precondition extraction

**问题**：M-005 需要 GPU 初始化、M-008 需要特定 loss scale。这些条件在 issue 中没写。

**如果解决**：给定 issue 描述 + fix commit diff + 框架源码，自动提取"完整的 bug 触发条件"。

**怎么解决**：
- LLM 分析 fix diff：哪些代码路径被修改了
- LLM 追溯：这些路径在什么条件下会被执行
- 输出：`{trigger_conditions: {tp_size: ">1", init_on_gpu: true, ...}}`

**验证**：对比 LLM 提取的 precondition vs 我们真实复现中发现的 precondition，计算 recall

### 贡献 3：跨版本 trace 注入

**问题**：每个 Megatron 版本的 API 不同，写一个通用 trace wrapper 几乎不可能

**如果解决**：一个 `inject_trace.py` 能自动适配任意版本的 Megatron/DeepSpeed/OLMo

**已经部分解决**：我们的 `inject_trace.py` 通过 monkey-patch `train_step` + try/except 多路径 import，已经能在多个 Megatron 版本上工作。

**论文价值**：这是 benchmark 基础设施的贡献——让后续研究者能复现我们的实验

### 贡献 4：侵入性 vs 覆盖率的量化框架

**问题**：之前没有人量化过"trace 改多少代码 → 能检测多少 bug"

**已经解决**：L0(20%) → L1(50%) → L3(95%)，基于 128 个 bug 的数据

**论文价值**：给实际部署提供工程指导——用户可以根据自己的需求选择侵入层级

---

## 四、总结：论文可以讲的"三个困难 + 三个解决"

| 困难 | 为什么难 | 我们的解决 |
|------|---------|----------|
| 不知道什么应该相同/不同 | invariant 的正确性取决于 topology | LLM 从源码提取 topology-aware parameter classification |
| 不知道 bug 的触发条件 | precondition 散落在代码执行路径中 | LLM 分析 fix diff + 源码追溯 trigger conditions |
| 不知道采什么数据 | trace schema 决定检测天花板 | 从 128 个 bug 反推最优 schema（27 字段覆盖 74%→95%） |

# 落地问题清单：Silent Error Detection 要真正 work 需要解决什么

> 按优先级排序。每个问题标注致命程度：🔴 不解决就全盘崩溃，🟡 不解决效果大打折扣，🟢 影响论文质量但不影响可行性。
> 每个问题后附 **状态** 字段，用于跟踪讨论进展。

---

## P0：能不能 work 的根本问题

### 🔴 P0-1. 你到底要检查什么？— Bug 的精确定义框架

**问题**：Silent error 不是一个精确定义的东西。同一个现象，在一种配置下是 bug，另一种配置下是 expected behavior。

| 现象 | ZeRO-0/1/2 下 | ZeRO-3 下 |
|------|-------------|----------|
| Optimizer state 跨 DP rank 不同 | Bug | Expected（sharded） |
| 参数 forward 前后 cksum 变了 | Bug | 可能 expected（offload） |

没有精确的 bug 定义，所有后续工作都没有 ground truth。需要一个清晰的框架：**"在配置 X 下，观测 Y 违反了算法 Z 的语义"**。

**需要回答**：
- 我们检测的 "silent error" 的边界在哪？
- 配置依赖的正确性怎么形式化？
- 是否有一种统一的方式表达 "什么配置下什么行为是正确的"？

**状态**：待讨论

---

### 🔴 P0-2. 正确性知识从哪来？

**问题**：检测能力的上限取决于能获取多少正确性知识。没有任何单一来源能给完整的知识。

| 知识来源 | 能提供什么 | 不能提供什么 |
|---------|-----------|------------|
| 算法论文（ZeRO, Megatron） | 高层算法应有的行为 | 具体实现的细节 |
| 框架源码 | 实现细节 | 设计意图（为什么这样写） |
| 框架文档 | 部分设计意图 | 通常不完整、可能过时 |
| Bug history（B1-B15） | 已知的出错模式 | 未知类型的 bug |
| Healthy trace | "正常情况是什么样" | "为什么是这样" |

**需要回答**：
- 依赖哪些来源、到什么程度？
- 不同来源之间矛盾时以谁为准？
- LLM 能从源码中理解到什么程度？理解不了的部分怎么办？

**状态**：待讨论

---

### 🔴 P0-3. Trace schema 决定了检测能力的天花板

**问题**：采不到的数据就检测不了相关的 bug。Schema 是 invariant 表达力的硬上限。

**当前能采的**：
- tensor 的 cksum / shape / dtype / norm（参数值级别）
- rank 的 dp/tp/pp 坐标（拓扑级别）
- step / stage（时间级别）

**当前采不到的**：
- 通信操作的具体内容（all-reduce 的输入输出）
- Activation tensor（中间层输出）
- 控制流信息（哪个 if branch 被执行了）
- 精确的时序（哪个 rank 先完成）
- micro_step 级别的 gradient accumulation 状态（当前是否区分？）

**需要回答**：
- B1-B15 的每个 bug，在当前 schema 下能否被区分出来？
- 如果不能，需要加什么字段？加了之后开销多大？
- schema 的最小完备集是什么——刚好覆盖所有目标 bug 类型？

**状态**：待讨论（建议最先做这个——逐个分析 B1-B15）

## P1：假设能 work，怎么保证效果

### 🟡 P1-4. False Positive 是用户信任的杀手

**问题**：一个系统如果报了 10 次警告、9 次是误报，用户就再也不看了。需要系统性地分析和消除 FP，而不是 case-by-case 打补丁。

**FP 的来源分类**：

| 来源 | 描述 | 举例 |
|------|------|------|
| Precondition 不全 | invariant 在某些合法配置下不成立 | ZeRO-3 下 optimizer state 本该不同 |
| Warmup transient | 前几步的状态不符合稳态 invariant | step=0 时参数尚未初始化完成 |
| Checkpoint 干扰 | 保存/加载 checkpoint 时状态暂时不一致 | checkpoint 写入时某些 rank 已更新、某些未更新 |
| 数值精度 | 不同 rank 的浮点计算顺序不同导致微小差异 | 非 bug 但 cksum 不同 |
| Intentional sharding | TP/ZeRO 有意让不同 rank 持有不同数据 | TP shard 的参数本该不同 |
| 采集时机偏差 | 不同 rank 的 hook 触发时机有微小差异 | 某 rank 在 allreduce 前采集，另一个在后 |

**需要回答**：
- 每种 FP 来源的处理策略是什么？
- 能否在 invariant 层面统一解决（通过完善 precondition），还是需要检测层面的后处理？
- FP rate 的可接受上限是多少？

**状态**：待讨论

---

### 🟡 P1-5. 怎么知道"没检测到"是没有 bug 还是检测不了？— Coverage 量化

**问题**：False Negative 比 FP 更隐蔽。系统说"一切正常"但其实有 bug 没被发现。

**FN 的来源**：
- **Invariant 覆盖盲区**：某类 bug 没有对应的 invariant
- **Bug signal 太弱**：数值上只有 1e-7 的差异，checksum 不同但统计量几乎一样
- **Bug 有延迟效应**：当前 step 的错误要到 N 步后才在可观测量中显现
- **采集频率不够**：每 K 步采集一次，bug 发生在中间的步

**需要回答**：
- 能否量化 invariant 库的覆盖率？覆盖了多少种已知 bug 类型？
- 有哪些 bug 类型是方法论上就覆盖不了的？（论文中应显式声明为 limitation）
- 有没有一种 coverage metric 能让用户知道"当前检测的置信度"？

**状态**：待讨论

---

### 🟡 P1-6. "Healthy trace" 怎么保证真的 healthy？— Bootstrapping 问题

**问题**：无论用 data-driven validation 还是 Daikon 式 falsification，都需要 healthy trace 做 ground truth。但如果 healthy trace 本身含有未被发现的 silent error，就会把错误状态当作正常。

**可能的缓解策略**：
1. 多版本交叉验证：用框架的多个版本跑 trace，版本间的差异需要调查
2. Single-GPU reference：关键 step 跑一个 single-GPU 版本对比
3. 数学性质锚点：某些 invariant 有数学保证（all-reduce 后梯度应相同），不需要从数据学习
4. 社区共识：使用广泛使用且被认为稳定的框架版本

**需要回答**：
- 哪种策略可行、开销可承受？
- 能否分层——部分 invariant 用数学保证锚定（最可靠），部分用 healthy trace 验证（次可靠）？
- 这个问题在论文中怎么处理？显式讨论为 limitation 还是提出解决方案？

**状态**：待讨论

## P2：工程落地的问题

### 🟡 P2-7. 运行时开销必须足够低

**问题**：生产训练中，每 1% 的开销 = 数万美元。5% 是可接受的上限。

**开销来源**：
| 来源 | 预估占比 | 可压缩空间 |
|------|---------|-----------|
| Trace 采集（cksum 计算） | ~3-4% | 参数采样、降低采集频率 |
| DuckDB 写入 | ~0.5-1% | 批量写入、异步 |
| SQL 查询执行 | ~0.5-1% | 层级化执行、只查 coarse |
| 存储 | 视保留策略 | 只保留最近 N 步 |

**需要回答**：
- 当前 TrainAudit 的实测开销分布是什么？瓶颈在哪？
- "全量采集 vs 采样采集" 对检测能力的影响多大？
- 能否做到"正常时 <2%，发现异常时升级到 5%"的 adaptive 开销？

**状态**：待讨论

---

### 🟡 P2-8. 不同并行配置的 invariant 适用性

**问题**：同一个 invariant 在 DP=4,TP=1 和 DP=2,TP=2 下可能完全不同。并行配置组合是一个大空间。

**配置维度**：
- DP size × TP size × PP size × CP size × EP size
- ZeRO stage (0/1/2/3)
- Gradient accumulation steps
- Distributed optimizer (on/off)
- CPU offload (on/off)
- Sequence parallel (on/off)

**需要回答**：
- invariant 是 config-parameterized 还是 config-specific？
- 在一种配置上验证的 invariant 在另一种配置上需要重新验证吗？
- 能否用 topology 信息自动推导 invariant 的适用范围？

**状态**：待讨论

---

### 🟢 P2-9. 框架版本更新会让 invariant 失效

**问题**：Megatron-LM 每月更新，重构可能让 invariant 失效。

**需要回答**：
- invariant 库的维护成本有多高？
- 能否检测到 invariant 失效（在新版本的 healthy trace 上不成立了）？
- 重新 mining 的成本是多少（时间/$$）？

**状态**：待讨论

## P3：论文层面的问题

### 🟢 P3-10. 和 baseline 的对比公平性

**问题**：TrainCheck 看 API trace，我们看 state trace。直接对比"检测率"可能不公平——检测的 bug 类型本来就不同。

**需要回答**：
- 怎么设计公平的 evaluation framework？
- 是否按 bug 类型分类对比？
- 是否需要在 TrainCheck 的强项（API-level bug）上也做实验？

**状态**：待讨论

### 🟢 P3-11. Bug benchmark 太小

**问题**：33 注入 + 15 真实 = 48 个样本。Reviewer 可能质疑统计显著性。

**需要回答**：
- 能否扩展 benchmark？从其他框架（DeepSpeed, OLMo, PyTorch FSDP）收集更多真实 bug？
- 注入 fault 的设计是否足够系统化？是否覆盖了所有 bug 类型？
- 是否需要做 ablation study 来增加评估的深度？

**状态**：待讨论

## 讨论顺序建议

```
第一轮（确定可行性）：
  → P0-3  逐个分析 B1-B15，验证 schema 能否覆盖
  → P0-1  从 B1-B15 的分析中归纳 bug 定义框架
  → P0-2  确定知识来源的优先级

第二轮（确定方法）：
  → P1-4  FP 处理框架
  → P1-6  Healthy trace bootstrapping
  → P2-8  Config-parameterized invariant

第三轮（论文设计）：
  → P1-5  Coverage 量化
  → P3-10 Evaluation 设计
  → P3-11 Benchmark 扩展

可以并行推进：
  → P2-7  开销测量（跑实验）
  → P2-9  版本更新影响评估
```

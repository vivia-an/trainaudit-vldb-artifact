# Semantic-Guided Predicate Discovery：方案总览

> 本文档记录从讨论中形成的新方案思路，供后续细化和实现参考。

---

## 1. 问题诊断：当前 TrainAudit 的核心矛盾

### 1.1 核心矛盾

**语义知识的广度** vs **实际检测需要的精准度**

- LLM 能理解算法描述（ZeRO 论文、Megatron 设计文档）中的设计意图
- LLM 能发现"这段代码和那段代码之间应该存在某种关系"
- 但 LLM **无法精确描述**这个关系是什么——用自然语言表述的 invariant 在翻译成 SQL 时必然有信息损失
- invariant 的 precondition（适用条件）永远写不全——body 容易写，precondition 散落在多个文档/PR/issue 中

### 1.2 invariant 粒度 trade-off

| 粒度 | 优势 | 劣势 |
|------|------|------|
| 粗粒度 | 适用范围广、precondition 少、false positive 少 | 可能漏检细粒度 bug |
| 细粒度 | 能精确捕获特定 bug | precondition 多、适用范围窄、容易 false positive |

最终目标是检测最大范围的 silent error——需要一种方法来**系统性地组织不同粒度的检查**。

### 1.3 现有 baseline 各自在哪里断裂

| 工作 | 知识来源 | 检测方式 | 断裂点 |
|------|---------|---------|--------|
| TrainCheck (OSDI'25) | Healthy trace 的 API 调用 pattern | 统计 pattern matching | Pattern 缺乏语义——不知道为什么应该成立，换 config 失效，无法区分 intentional sharding 和真 bug |
| TTrace (arXiv) | Trusted reference implementation | 逐 tensor 对比 | Reference 不可得/不可对齐——生产训练没有 reference，分布式和 single-GPU 对齐困难 |
| TrainVerify (SOSP'25) | Formal logical specification | Plan 等价性证明 | 只覆盖 plan 不覆盖 runtime state——无法检测 gradient buffer 意外 reset 这类状态级 bug |
| 当前 TrainAudit | 框架源码/文档（LLM 提取） | NL invariant → SQL | NL→SQL 信息损失 + precondition 写不全 |

## 2. 核心思路：语义引导 + 数据驱动

### 2.1 一句话

> LLM 不生成 invariant，只生成 **搜索方向**；精确的 invariant 从 trace 数据中**自动发现**。

### 2.2 四层 pipeline

```
Layer 1: Semantic Hypothesis Generation (LLM)
    ↓ 输出：结构化搜索指令（哪些实体 × 哪些维度 × 什么类型的关系）
Layer 2: Predicate Enumeration (自动化)
    ↓ 输出：候选 predicate 集合（SQL / formal predicate）
Layer 3: Data-Driven Validation (Healthy trace)
    ↓ 输出：verified invariant（在 healthy trace 上始终成立的 predicate）
Layer 4: Semantic Filtering (LLM)
    ↓ 输出：final invariant library（过滤掉 spurious pattern）
```

### 2.3 每层的角色分工

| 层 | 谁做 | 做什么 | 解决什么问题 |
|----|------|--------|-------------|
| Layer 1 | LLM | 提供搜索方向 | 避免 TrainCheck 式盲搜 |
| Layer 2 | 模板引擎 | 枚举候选 predicate | 避免 NL→SQL 信息损失 |
| Layer 3 | Healthy trace 数据 | 筛选出真正成立的 predicate | 提供 ground truth（替代 SMT solver） |
| Layer 4 | LLM | 过滤无语义意义的 spurious pattern | 避免 TrainCheck 的 FP 问题 |

---

## 3. 定位：vs 所有 baseline

| vs 谁 | 差异 |
|-------|------|
| vs TrainCheck | 搜索有语义方向，不盲搜；能覆盖 topology-aware 语义关系 |
| vs TTrace | 不需要 reference implementation，用 semantic hypothesis + healthy trace 替代 |
| vs TrainVerify | 覆盖 runtime state 转移，不只是 execution plan |
| vs 当前 TrainAudit v1 | 不做 NL→SQL 翻译；LLM 只提供方向，精度来自数据 |

## 4. SE 领域的支撑：已有类似范式

这个 "LLM 提供搜索方向 + 传统工具精确化" 的范式在 SE 领域已被验证：

| SE 工作 | LLM 角色 | 精确化工具 | Venue |
|---------|---------|-----------|-------|
| LLift | 回答 static analyzer 的语义问题 | Static analyzer (path analysis) | OOPSLA'24 |
| KNighter | 从 patch 学 bug pattern → 生成 checker | Coccinelle + patch 验证 | SOSP'25 |
| LaM4Inv | 提供 predicate candidates | BMC + SMT solver | ASE'24 |
| RunVS | 提供 predicate 搜索方向 | Decision tree + program runs | SAC'25 |
| GPTAid | 生成 API 安全规则 | Execution feedback | NDSS'25 |

我们的工作是这个范式在 **distributed training silent error detection** 领域的实例化，其中 "精确化工具" 是 **healthy trace 数据 + topology-aware predicate enumeration**。

## 5. 论文故事（draft）

> Silent error detection 的核心困难是获得 correctness oracle——判断"在当前配置下，这个运行时状态是否正确"的依据。
>
> 现有方法从不同来源获取这个 oracle，但都在特定环节断裂：TrainCheck 从 trace 数据中学习 pattern，但 pattern 缺乏语义根基，无法区分 intentional 变化和真实故障；TTrace 从 reference implementation 获得精确的值级信号，但要求离线执行且 reference 可得；TrainVerify 从 formal specification 获得证明级保证，但只覆盖 plan 而非 runtime state。
>
> 我们观察到：框架源码和文档中蕴含了丰富的 semantic knowledge（设计意图、并行策略的正确性条件、状态同步的时序要求），而训练的 runtime trace 提供了精确的观测数据。两者单独都不能构成 oracle——语义知识有广度但不精确，trace 数据精确但没有"应该是什么"的判断。
>
> 我们提出 semantic-guided predicate discovery：用 LLM 从源码/文档提取 topology-aware semantic hypothesis（指定在哪些实体、哪些 rank 维度、哪些 stage 之间应该存在什么类型的关系），然后在 hypothesis 指定的子空间内，用 healthy trace 数据驱动地发现精确的 predicate，最后用语义上下文过滤 spurious pattern。

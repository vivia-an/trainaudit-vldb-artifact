# 复现实验经验总结

> 基于 M-005 和 M-008 的真实 Megatron 复现过程，记录遇到的问题、得到的 insight、对论文方向的启示。

## 2. 暴露的核心问题

### 问题 1：Invariant 不知道"什么应该相同、什么应该不同"

INV-001 检查"所有参数跨 TP rank 一致"，但 TP 下：
- `query_key_value.weight`、`dense.weight` 等 → **应该不同**（TP shard）
- `router.weight`、`norm.weight/bias` 等 → **应该相同**（不参与 TP shard）

一个没有 semantic knowledge 的 invariant 无法区分这两类参数。它要么全查（FP 爆炸），要么不查（漏检）。

**启示**：这正是论文的核心论点——**检测 silent error 需要 semantic knowledge 来判断"在这个配置下，哪些关系应该成立"**。

### 问题 2：Bug 的触发条件比 issue 描述的更具体

| Bug | Issue 描述的触发条件 | 实际需要的额外条件 |
|-----|-------------------|------------------|
| M-005 | TP > 1, 使用 SwitchMLP | + GPU 初始化（非 CPU 初始化） |
| M-008 | --overlap-param-gather + --overlap-grad-reduce | + FP16 + 足够大的 loss scale 让 found_inf 机制参与 |

这些"额外条件"不在 issue 里，需要深入理解代码才能知道。

**启示**：bug 的 precondition 不完整是常态，不是异常。论文之前讨论的"precondition 写不全"问题在实践中完全被验证了。

### 问题 3：数据驱动的 baseline 学习可能不可行

之前讨论的方案是"从 healthy trace 学习 invariant"。但实验发现：
- buggy 和 fixed 版本在某些配置下的 trace **完全相同**（M-008 用 `--initial-loss-scale 1` 时）
- 参数在 TP 下本来就不同，"什么是 healthy"取决于配置

**启示**：纯数据驱动的方法（如 TrainCheck 的 trace pattern matching）在这里失效——它能学到"TP 下 qkv.weight 在两个 rank 上不同"，但不知道这是正常的还是 bug。

## 3. 关键 Insight：三个层次的知识

复现实验揭示了检测 silent error 需要三个层次的知识，缺一不可：

### ���次 1：Schema 知识（采什么数据）

我们的 sdctrace 系统已经解决了这一层：27 个字段、3 个 hook 点、覆盖 74% 的 bug。

**已验证**：真实 Megatron 训练中，sdctrace 能正确采集 492 rows/run 的完整 trace 数据。

### 层次 2：Topology 知识（什么配置下哪些参数有什么关系）

这是当前最大的缺口。需要知道：

| 配置 | 参数类型 | 跨 rank 关系 |
|------|---------|-------------|
| TP=2 | qkv.weight | 不同（TP shard） |
| TP=2 | router.weight | 应该相同 |
| TP=2 | norm.weight | 应该相同 |
| DP=2 | 所有参��� | 应该相同（optimizer step 后） |
| PP=2 | stage 0 的参数 | 只存在于 pp_rank=0 |

这些关系**不是从数据中学到的**——需要从 Megatron 的源码/文档中提取。

**这正是 LLM semantic knowledge 的用武之地**：LLM 能理解"TP shard 的参数有哪些"、"router 不参与 TP shard"等设计意图。

### 层次 3：Bug Precondition 知识（什么条件下 bug 会触发）

最深层的知识——不仅要知��"什么关系应该成立"，还要知道"这个 bug 在什么环境条件下会破坏这个关系"。

例如 M-005：
- invariant：router.weight 跨 TP rank 应一致
- precondition：仅在 GPU 初始化路径下违反（CPU 初始化不受影响）

这个 precondition 在 issue #599 中没有提到，需要深入代码分析才能知道。

## 4. 对论文方向的启示

### 4.1 当前方案（v1 TrainAudit）的验证

v1 论文声称"从源码/文档自动挖掘 topology-aware invariant"——复现实验证明了这个方向是对的：

- ✅ 需要 topology-aware：INV-001 不区分 TP shard → FP 爆炸
- ✅ 需要 semantic knowledge：bug 触发条件散落在多处，trace pattern 无法推断
- ✅ 需要 precondition：同一个 invariant 在不同 init 路径下对错不同

### 4.2 新方案（v2 semantic-guided）的定位更清晰

之前讨论的 v2 方案（LLM 提供搜索方向 → 数据驱动精确化）需要修正：

| 原始假设 | 实验验证 | 修正 |
|---------|---------|------|
| "从 healthy trace ��习精确 invariant" | 不可行——buggy/fixed 在某些配置下 trace 相同 | 需要 semantic knowledge 来定义"什么是正确的"，不能只靠数据 |
| "cross-rank equality 是最重要的 invariant" | 只覆盖 20% 的 bug，且 TP 下大量 FP | 需要 topology-aware 的 invariant |
| "precondition 可以从多配置 trace 自动发现" | 部分可行，但 bug 触发的环境条件（CPU/GPU init）无法从 trace 推断 | Precondition 需要分两类：配置类（可从 topology 推断）+ 环境类（需要源码分析） |

### 4.3 论文的核心贡献可以重新框架化

> **检测 silent error 需要三层知识：schema（采什么）→ topology（什么关系）→ precondition（什么条件下成立）。现有方法只覆盖了第一层（TrainCheck 的 trace pattern）或部分第二层（固定的 invariant template）。我们的贡献是：用 LLM 从源码/文档中提取第二层和第三层的知识，使检测覆盖率从 20% 提升到 X%。**

### 4.4 Benchmark 本身也是贡献

复现实验过程中积累的基础设施本身有价值：
- 128 个真实 bug 的结构化记录（category、parallel_dimension、required_trace_fields、detection_signal）
- sdctrace 工具（框架无关的 trace 系统，2 行代码接入）
- pretrain_wrapper.py（跨版本 Megatron pretrain，随机数据，零依赖）
- 侵入性 vs 覆盖率的量化分析（L0-L4，20%→95%）

这些可以作为一个独立的 benchmark dataset 发布。

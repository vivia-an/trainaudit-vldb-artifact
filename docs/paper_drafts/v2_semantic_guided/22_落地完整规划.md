# TrainAudit 落地完整规划：从 T0 原型到投稿就绪

> 本文是 `21_落地roadmap.md` 的上层补充。doc 21 规划了系统下半截（trace 收集 + 手写 Python rule，已 Phase 1 完成）；本文规划上半截（不变量 DSL、LLM 自动挖掘、根因定位、大规模评测、baseline 对比），把原型推到投稿候选状态。
>
> 时间预算：单人 5–6 周，采用 **evidence-first / gate-based** 推进。默认目标不是一口气承诺 80 bug + 全 4 层 LLM 全部完成，而是先过 5 个硬门槛：benchmark manifest → DSL 等价 → clean FP/overhead → 32/48 bug 主表 → mining/LLM 扩展。
>
> 硬约束：每个工作项必须配可量化的"如何测试"小节，**优先用已 reproduced 的 bug 做正例验证**，fixed-commit 做反例验证；所有 paper 数字必须同步到 `22_paper_evidence_index.md` 后才能写进正文。

## Context：为什么需要本规划

doc 21 完成后系统状态：
- ✅ PyTorch 核心 hookpoint + DuckDB trace store（dist / module / optim / clip_grad / scheduler / checkpoint / dataloader / functional / build 等）
- ✅ 13 条手写 Python T0/T1 rule

**论文 (§3.2 / §3.4) 的真正卖点**（doc 01 §2.2）：
- LLM 语义引导 + 数据驱动 4 层 pipeline
- 不变量 → SQL 自动检测
- 根因定位

**这部分目前 0% 实现**。如果停留在 doc 21 进度，整篇论文会被 reviewer 判定为"trick + 手工标注"。本规划补齐 5 个 workstream（A–E），把缺口补上。

**预期产出**：
- Gate 1：DSL 化的不变量库（核心 rule 用 4 模板表达；复杂 active-probe rule 明确列为 probe-derived / Python fallback）
- Gate 2：DSL → SQL 与现有 Python rule 在真实 trace 上 event_id 等价

- Gate 4：32/48 bug 主评测表（80 bug 作为 stretch，而不是 Week 1 承诺）
- Gate 5：deterministic mining（Layer 2/3）先落地；LLM Layer 1/4 和 RCA 作为 paper story 的扩展证据
- Baseline：TrainCheck 在同一 selected_32/48 子集上做可运行对比；80 bug baseline 仅在 harness 稳定后扩展

## 2. Workstream A：不变量 DSL + SQL 编译器

> 把现有 13 条 ad-hoc Python rule 抽象为结构化 DSL（YAML），编译成 DuckDB SQL。这是 §3.2/§3.4 的论文骨架，也是 Workstream B（LLM mining）的目标语言。

### A1 — 4-template DSL schema（P0，3 day）
**产出**：
- `trainaudit/trainaudit/dsl/predicate.py`（dataclass：`Predicate / Scope / Bound / Precondition / Tolerance`）
- `trainaudit/trainaudit/dsl/templates.py`（4 模板）
- `trainaudit/trainaudit/dsl/loader.py`（YAML → `Predicate`，schema 校验）
- `trainaudit/trainaudit/dsl/registry/T0/*.yaml`（≥7 条 rule 的 YAML 版本）
- `trainaudit/tests/dsl/test_loader.py`

**DSL 字段（最小集）**：`id, family, template, scope.{hookpoint, module_class_regex, payload_path}, predicate.{kind: bound|equality|present|monotonic}, precondition.expr, tolerance.{abs, rel, quantile_pct}, evidence_bugs[]`

**测试**：
- 正例（必须全 parse 成功）：把 `T0_clip_grad_bounded / T0_softmax_degenerate / T0_no_nan_inf / T0_token_id_range / T0_initial_lr_present / T0_norm_output_rms / T1_replica_cksum_equal` 共 7 条改写为 YAML
- 反例（5 个故意错的 YAML）：缺 hookpoint / tolerance 负数 / template 拼错 / payload_path 不合规 / 引用不存在的 family — loader 必须报清晰错误
- 命令：`pytest trainaudit/tests/dsl/`
- 通过判据：13/13 现有 rule 完成"可 DSL 表达 / probe-derived / Python fallback"归类；核心 7 条 YAML parse 成功；5/5 错误样例报错；DSL spec 文档 1 页
- 失败应对：先怀疑 4 模板是否覆盖 softmax-degenerate 这种内嵌 `l2² ≈ n_rows` 逻辑——若不能直接表达，加一个 `tensor_signature` 二级算子，**不要**回退到嵌入自由 Python

### A2 — DSL → DuckDB SQL 编译器（P0，4 day，依赖 A1）
**产出**：
- `trainaudit/trainaudit/dsl/compiler.py`（`Compiler.compile(pred) -> CompiledRule(sql, postprocess)`）
- `trainaudit/trainaudit/dsl/sql_fragments.py`（payload 路径 → DuckDB `json_extract`；shape → n_rows）
- `trainaudit/trainaudit/dsl/runner.py`（与现有 `verifier.py:run_rules` 共存，让 DSL rule 与 Python rule 并行跑）
- `trainaudit/tests/dsl/test_compiler_equivalence.py`

**测试（SQL 等价回归 — 这是 A2 的灵魂）**：
- 正例 trace：`exp/data/reproductions/M-005/trace_buggy/coredump_dp0_tp0_pp0_cp0_ep0.db` + 5 个 `benchmark/bugs/*/trainaudit_run.sh` 跑出来的活体 trace
- 对 5 个 bug（**B11 / M-014 / O-NEW-1 / M-005 / B12**）的 DSL rule 与对应 Python rule，**violation event_id 集合必须完全相等**
- 反例：`exp/data/reproductions/M-005/trace_fixed/` + 5 个 fixed-commit run 上 DSL/Python 都必须 0 violation
- 命令：5 个 driver 改加 `--use-dsl-rules` flag，diff 输出
  ```bash
  bash benchmark/bugs/B11/trainaudit_run.sh && bash benchmark/bugs/M-014/trainaudit_run.sh && \
  bash benchmark/bugs/O-NEW-1/trainaudit_run.sh && bash benchmark/bugs/O-005/trainaudit_run.sh && \
  bash benchmark/bugs/B12/trainaudit_run.sh
  ```
- 通过判据：5/5 bug 上 DSL/Python violation 数差 == 0；fixed 上都 0/0
- 失败应对：先看 `json_extract(payload, '$.output.l2_norm')` 在 `:memory:` vs 文件 db 行为；不要先怀疑 template 设计

### A3 — 剩余 rule 表达性收口（P1，3 day，依赖 A2）
**产出**：
- 13 条现有 rule 的 `MAPPING.md`：每条标注 `dsl_native / probe_derived / python_fallback`
- 尽量把剩余 6 条改写为 YAML；明确不能自然表达的 rule 保留 Python fallback，并解释为什么

**约束**：
- 扩展 template 字段不超过 2 个，否则 paper "4-template" story 失效
- 不为追求 13/13 YAML 而塞自由 Python；`T1_residual_stream` 这类 active probe 可以作为 probe-derived predicate 单独叙述

**测试**：在 B12 / O-005 / M-NEW-1 / M-020 / B1 / O-NEW-7 的 buggy/fixed 对上回归；对 `dsl_native` rule 要求 DSL/Python violation event_id 完全一致；对 fallback rule 要求 verifier 共存且结果不回退

## 3. Workstream B：LLM 自动挖掘 4 层 Pipeline

> doc 01 §2.2 的核心方法。Layer 2/3 是确定性主线（P0），Layer 1/4 是 LLM 扩展（P1-gated）：只有在 M1 DSL 等价和 M2 clean FP/overhead 过关后，才把 LLM 层推进到 paper 主表口径。这样可以保住方法论证据，不把投稿风险压在 LLM 稳定性上。

### B1 — Layer 2: 模板枚举器（P0，4 day，依赖 A1）
**产出**：
- `trainaudit/trainaudit/mining/hypothesis_schema.py`（`Hypothesis(entities, dimensions, relation_type, scope_hint)`）
- `trainaudit/trainaudit/mining/layer2_enumerate.py`（Hypothesis + trace schema 自省 → ≤200 候选 Predicate）
- `trainaudit/tests/mining/test_enumerate.py`

**测试**：
- 正例：手写 6 个 hypothesis（cross-rank-equality / tensor-stat-bound / payload-field-compare / cross-step-monotonic / structural-presence / conditional），枚举出的候选必须包含已知 rule 的等价物（如 cross-rank-equality 必须枚举出 `T1_replica_cksum_equal` 等价 predicate，用 sqlglot AST 比较）
- 反例：scope 给一个不存在的 hookpoint，返回空列表而非崩溃
- 通过判据：6/6 hypothesis 各产 5–50 候选；至少 1 候选与已 DSL 化 rule 等价
- 失败应对：先查 enumerate 是否在 schema 自省时把 payload JSON 字段推全（`json_keys`）

### B2 — Layer 3: Healthy trace validator + auto-precondition（P0，5 day，依赖 B1）
**产出**：
- `trainaudit/trainaudit/mining/layer3_validate.py`（多 trace 投票 + tolerance quantile_pct 自动学习）
- `trainaudit/trainaudit/mining/precondition_inference.py`（按 doc 05 §2.3：H1/H2 成立、H6 不成立 → 推 `zero_stage<3`）

**Healthy trace 来源**（**不要新写采集器**，复用 `exp/sdctrace/auto.py`）：
- 已有：`exp/data/reproductions/M-005/trace_fixed/*.db`
- 用 `exp/sdctrace/benchmark/runner.py` 跑 4 个新配置：DP-only / TP=2 / ZeRO-1 / ZeRO-3

**测试**：
- 正例：把 B1 上"router weight cksum 在 TP group 内相等"丢进去，4–6 个 healthy config 全部成立 → 升格为 verified invariant；在 M-005 buggy trace 上必须 fire
- 反例：把"所有参数 norm 跨 step 单调下降"丢进去，validator 返回 reject + 列出反例 step
- 命令：`python -m trainaudit.mining.layer3_validate --hypotheses tests/mining/fixtures/hyp_set.yaml --healthy-traces exp/data/reproductions/M-005/trace_fixed --out output/verified.yaml`
- 通过判据：≥80% 候选被正确分类；自学的 tolerance 与硬编码值差 ≤2x
- 失败应对：先怀疑 healthy trace 数量不够，加 1 个新配置；不要急调 validator 阈值

### B3 — Layer 1: LLM hypothesis 生成（P1-gated，3 day，依赖 B1+B2+M1+M2）
**产出**：
- `trainaudit/trainaudit/mining/layer1_hypothesis.py`（接 `claude-proxy-v3.py`）
- `trainaudit/trainaudit/mining/prompts/hypothesis_v1.txt`

**测试（端到端 L1→L4）**：
- 正例：喂 5 段已知 bug 相关源码（router.py / clip_grad.py / bf16_optimizer.py / checkpoint.py / rmsnorm.py），LLM 至少为每段产 1 hypothesis，**该 hypothesis 经 B1+B2 后能定位到该 bug 应当 fire 的 rule**
- 反例：喂一段无关代码（logging utility），LLM 不应硬编
- 通过判据：5 个目标 bug（**B11 / M-014 / O-NEW-1 / O-005 / B12**）至少 4 个的 hypothesis 能驱动后续 layer 重新发现已 DSL 化的 rule
- 失败应对：先看 prompt 是否给出 Hypothesis 结构化 schema 示例

## 4. Workstream C：根因定位（Diagnosis Verifier）

> §3.4 卖点之二。当前 verifier 只输出"X 条违规"，需要扩展到 module/rank/step + 嫌疑代码段。

### C0 — Trace context metadata 补齐（P0，2 day，依赖现有 hook）
**为什么先做**：当前 event schema 足够检测 violation，但不足以稳定诊断"调用点 / module name / 参数名 / 源码位置"。如果不先补上下文，C1 很容易只能输出 `module_class=RMSLayerNorm` 这类弱定位。

**产出**：
- module hook payload 增加 `module_name`（通过 install 时注入 name map）、`module_id`、可选 `callsite`
- functional / checkpoint / clip_grad hook payload 增加 `fn`、`callsite.file`、`callsite.line`（失败时为 null，不阻塞训练）
- build snapshot 中参数条目保留 `param_name`、`module_name`、`semantic`
- `trainaudit/tests/test_trace_context.py`

**测试**：
- toy model 上 `module.fwd.post` 至少 90% 事件有 `module_class + module_id`，命名模块有 `module_name`
- B11 / M-014 / O-NEW-1 trace 中 violation event 能回溯到 `fn/module_class/module_name` 至少一个强定位字段
- callsite 缺失时 verifier 不崩溃，只降级为 class/module 级诊断

### C1 — Violation context expander（P0，4 day，依赖 A2+C0）
**产出**：
- `trainaudit/trainaudit/diagnosis/expander.py`（event_id → 前后 N step 同 rank/同 module trace 切片）
- `trainaudit/trainaudit/diagnosis/cross_rank_outlier.py`（同 step 跨 rank 比对，找 outlier rank）
- `trainaudit/trainaudit/diagnosis/report.py`（`DiagnosisReport(rule_id, suspect_module, suspect_rank, suspect_step, context_events, hypothesis_text)`）

**测试**：
- 正例（4 bug）：
  - **B11**：expander 必须定位到 `clip_grad_norm_` 调用点 + 给 pre/post norm
  - **M-005**：必须定位到 router.weight + 标 outlier rank
  - **M-014**：必须定位到 router 模块 + softmax 输出 abs_max
  - **O-NEW-1**：必须定位到 RMSLayerNorm 模块
- 反例：clean run（fixed commit）上 expander 不应被调用——若被调用，输出 "no violation, no diagnosis" 而非空 stack
- 命令：扩展 4 个 `trainaudit_run.sh` 在 violation 后调 `trainaudit.diagnose(results)`，对比 expected suspect
- 通过判据：4/4 正例的 `suspect_module/suspect_rank/suspect_step` 字段非空且与 `config.json:root_cause` 吻合

### C2 — LLM RCA agent（P1，2 day，依赖 C1）
**产出**：`trainaudit/trainaudit/diagnosis/rca_agent.py`（`DiagnosisReport` → LLM → "嫌疑代码段 + 修复建议"）
**测试**：8 bug（**B11 / B12 / M-005 / M-014 / O-005 / O-NEW-1 / OC-NEW-1 / M-020**）上跑，人工评估 hypothesis 是否指向真实根因（按 `config.json:root_cause`）。**目标 5/8 命中**，paper 给定性表 + 1 个 case study

## 5. Workstream D：大规模评测 Harness

> benchmark 池规模是底气，但当前可直接评测的 bug 少于原始配置数；先做 manifest 和 32/48 主表，再把 80 bug 作为扩展目标。

### D0 — Benchmark manifest 清洗（P0，2 day，**关键路径前置**）
**为什么先做**：当前没有统一 `status.json`，只有部分 `config.json` 带 `reproduction_status`；`detect.py` 和 `trainaudit_run.sh` 覆盖也不完整。所有 32/48/80 bug 目标必须从 manifest 出发，否则评测计划会建立在错误前提上。

**产出**：
- `benchmark/eval/build_manifest.py`
- `benchmark/eval/manifest.json`
- `benchmark/eval/manifest_summary.md`

**manifest 字段**：
`bug_id, framework, category, reproduction_status, has_detect_py, has_reproduce_sh, has_trainaudit_driver, gpu_needed, buggy_commit, fixed_commit, expected_output, detection_method, root_cause`

**测试**：
- 本地扫描结果必须能复现以下数量级：`config.json ~= 295`、`detect.py ~= 64`、`trainaudit_run.sh ~= 10`、`reproduction_status=reproduced ~= 33`
- manifest 每行都有 `source_config_path`，任何缺字段 bug 都标 `missing_fields[]` 而不是丢弃
- `manifest_summary.md` 按 framework/category/status 输出 top-level 表，手动检查 5 个已知 bug（B11 / B12 / M-014 / O-005 / O-NEW-1）字段正确

### D1 — 32/48 bug 主评测 harness（P0，6 day，依赖 D0+A2；C1 可并行，**关键路径**）
**产出**：
- `benchmark/eval/select_subset.py`（从 manifest 中按 reproduced / driverable / oracle 状态选 `selected_32.json`，条件满足后扩到 `selected_48.json`）
- `benchmark/eval/run_all.py`（批量调每个 bug 的 `trainaudit_run.sh`，buggy/fixed 各 1 次，写 results.csv）
- `benchmark/eval/grade.py`（detection rate / FP / category breakdown）
- `benchmark/eval/gen_driver.py`（**关键**：从 `config.json:framework + reproduce.sh` 自动派生 `trainaudit_run.sh`，优先把 driver 数从约 10 扩到 32/48；每个自动生成 driver 必须有 smoke status）

**子集结构（分阶段，而不是一次性承诺 80）**：
- `selected_32`：只选 reproduced + driverable 优先；framework 尽量覆盖 Megatron / DeepSpeed / OLMo / OLMo-core；类别覆盖 numerical / dtype / checkpoint / gradient_sync / data_loading / communication 等高频类
- `selected_48`：在新增 driver 后扩展，作为 paper 主表目标
- `selected_80`：仅当 generator 和 fixed-run 稳定后作为 stretch；不作为前 4 周验收标准

**测试**：
- 正例：`selected_32` 中至少 24 个 buggy run 完整跑通；`selected_48` 中至少 36 个 buggy run 完整跑通
- 检测率：如实报告 T0/T1/DSL 当前覆盖，不在 D1 阶段硬承诺 50/80；paper-ready 目标是先把真实 cover rate 从当前 6/48 推到 ≥15/48，若达不到则改写 claim 为 pilot evaluation
- 反例：可执行 fixed-commit 上 FP_rate ≤ 0.05；外加 `benchmark/eval/clean_runs/{toy_mlp,megatron_tiny,olmo_tiny,deepspeed_tiny}.py` 尽量 0 violation
- 命令：改造 `benchmark/run_on_gpu.sh` 调 `eval/run_all.py`
- 通过判据：产出 `results.csv` + `failures.csv` + `paper_table_coverage.md`，每个失败都有 `fail_stage`（checkout / install / reproduce / trainaudit / fixed / oracle）
- 失败应对：先看 generator 是否漏了某 framework 的 PYTHONPATH/elastic-shim（B11 driver 的 `_t_api.log` shim 是必须的）；其次看 subset 是否混入没有 reproduced 状态或缺 oracle 的 bug

### D2 — 80 bug 扩展评测（P1/stretch，5 day，依赖 D1 稳定）
**产出**：`selected_80.json` + 80 bug `results.csv`
**进入条件**：
- `selected_48` 已经有 ≥36 个 buggy run 成功
- fixed FP 口径可执行，且 failure taxonomy 清晰
- driver generator 新增 bug 的 smoke success ≥70%

# 论文贡献重新定位：困难本身就是贡献

> 基于复现实验的真实经验，重新思考论文的 contribution 结构。

---

## 核心观点

**复现 bug 的数量是结果，不是贡献。贡献是复现过程中暴露出来的困难，以及我们解决这些困难的方法。**

审稿人不会因为"我们检测了 90% 的 bug"买单——他们会问"为什么这件事很难？你做了什么别人做不了的？"

---

## 1. 我们实际遇到的困难（按复现实验的真实经验）

### 困难 1：你不知道"什么应该相同"

最直觉的检测方法是 cross-rank 比较：两个 rank 的参数不一样 → bug。

但真实实验告诉我们：**TP 下大部分参数本来就不一样**。`query_key_value.weight` 在 tp_rank=0 和 tp_rank=1 上是不同的 shard——这是正确的。只有 `router.weight`、`norm.weight` 这些不参与 TP shard 的参数应该一样。

知道"哪些参数应该相同、哪些应该不同"需要理解 Megatron 的 TP 分片策略。这个知识：
- 不在 trace 数据中（数据只告诉你"不同"，不告诉你"应该不同"）
- 不在一个统一的文档中（散落在 ColumnParallelLinear、RowParallelLinear 等不同类的实现里）
- 随着并行配置变化（TP=1 时所有参数都应该相同，TP=2 时部分不同）

**这是 semantic knowledge 的第一个硬需求：topology-aware parameter classification。**

### 困难 2：Bug 的触发条件比描述的更多

M-005 的 issue 说"TP > 1 时 router weight 不同步"。但真实复现发现：
- CPU 初始化时不触发（所有 rank 共享 CPU RNG）
- 只在 GPU 初始化路径下触发（每个 rank 有不同的 CUDA RNG seed）

M-008 的 issue 说"overlap-param-gather + overlap-grad-reduce 导致 LR=0"。但真实复现发现：
- 需要 FP16（BF16 没有 loss scaling 机制，bug 不触发）
- 需要初始 loss scale 足够大以触发 overflow → found_inf 机制

**每个 bug 都有"隐藏的 precondition"——在 issue 中没有写明，在 fix commit 的 diff 中也看不出来，只有深入理解代码执行路径才能知道。**

**这是 semantic knowledge 的第二个硬需求：precondition extraction。**

### 困难 3：同一条 invariant 在不同配置下正确性不同

"optimizer state 跨 DP rank 一致"——这条规则在 ZeRO-0/1/2 下是对的，在 ZeRO-3 下是错的（state 被 shard 了）。

"参数在 optimizer step 后应该变化"——这条规则对 requires_grad=true 的参数是对的，对 frozen weight 是错的。

**一条 invariant 的对错取决于运行时的配置上下文，不存在"普适的 invariant"。**

**这是 semantic knowledge 的第三个硬需求：configuration-conditional invariant。**

### 困难 4：trace 数据的侵入性和覆盖率存在 trade-off

我们量化了这个 trade-off（文档 11 和 12）：

| 侵入层级 | 代码改动 | 覆盖率 | 关键发现 |
|---------|---------|--------|---------|
| L0（2 行） | 零侵入 | 20% | 只能做 cross-rank equality |
| L1（+统计量） | 5 行 | 50% | 加 norm/mean 开销反而更低 |
| L3（+framework hook） | 150 行 | 95% | 需要了解 Megatron 内部结构 |

L0→L1 的跃升最大（+30%），但 L1→L3 需要 framework-specific knowledge——又回到了 semantic knowledge。

## 2. 贡献的重新框架化

### 不再是"检测系统"的故事，而是"知识需求"的故事

旧框架：
> 我们做了一个系统，能检测 90% 的 silent error。

新框架：
> 检测 silent error 需要三层知识，现有方法缺少后两层。我们通过真实复现 128 个 bug 的经验，首次系统性地揭示了这个知识需求，并展示了 LLM 如何填补这个 gap。

### 三层知识框架（核心 contribution 1）

| 层 | 知识内容 | 来源 | 现有方法覆盖？ | 我们的方法 |
|----|---------|------|-------------|----------|
| **L1 Schema** | 采什么数据（cksum、grad_norm、loss...） | 工程设计 | ✅ TrainCheck、我们的 sdctrace | 从 128 个 bug 的 required_trace_fields 反推最优 schema |
| **L2 Topology** | 什么配置下什么参数有什么关系 | 框架源码中的 TP/PP/DP 分片逻辑 | ❌ TrainCheck 不知道、TTrace 不需要 | LLM 从源码提取 parameter classification |
| **L3 Precondition** | 什么环境条件下 invariant 成立 | 散落在 issue/PR/commit/文档中 | ❌ 没有人做过 | LLM 从多源信息综合提取 |

**这个框架本身就是一个 contribution——它解释了为什么现有方法在某些 bug 上失败。**

### 128 个 bug 的量化分析（核心 contribution 2）

不是"我们找到了 128 个 bug"，而是：

> 我们对 128 个真实 bug 做了结构化分析，发现：
> - 只有 20% 能通过 cross-rank equality 检测（L1 schema 足够）
> - 34% 需要 bounded_change 检测（需要 L2 topology 知识判断"正常变化范围"）
> - 37% 与并行策略无关（需要 L3 precondition 知识判断"什么条件下成立"）
> - 当前 schema 只覆盖 30%，补充 5 个字段后覆盖 70%，加 framework hook 后 95%

**这些数字本身就是 contribution——之前没有人系统量化过 silent error 检测的知识需求。**

### 侵入性 vs 覆盖率的 trade-off（核心 contribution 3）

> 我们首次量化了 trace 侵入程度和 bug 覆盖率之间的关系，发现：
> - L0→L1 的跃升最大（+30%），且开销反而降低
> - L3 的 95% 覆盖率需要 framework-specific knowledge
> - 最后 5%（L4）需要 NCCL hook，代码量暴增但覆盖率增益微小

**这给实际部署提供了工程指导——用户可以根据需求选择侵入层级。**

### 真实复现的经验报告（核心 contribution 4）

> 我们尝试在真实 Megatron 环境中端到端复现 bug，发现：
> - Bug 的触发条件比 issue 描述的更多（M-005 需要 GPU init，M-008 需要特定 loss scale）
> - 同一条 invariant 在不同配置下可能是 TP/FP（TP shard 问题）
> - 纯数据驱动的 baseline 学习不可行（buggy/fixed 在某些配置下 trace 完全相同）

**这些发现只有通过真实复现才能获得——paper survey 和理论分析发现不了。**

## 3. 论文结构建议

### 标题方向
不再是"检测系统"的标题，而是"知识需求"或"benchmark + 方法"：

- "What Does It Take to Detect Silent Errors in Distributed Training? A Three-Layer Knowledge Framework"
- "Beyond Trace Patterns: Why Detecting Silent Errors Requires Semantic Knowledge from Source Code"
- "SDC-Bench: A Benchmark and Knowledge Framework for Silent Error Detection in LLM Training"

### Section 结构

**§1 Introduction**
- 从复现经验引入：我们尝试检测 128 个真实 bug，发现 cross-rank 比较只能覆盖 20%
- 核心问题：为什么这么低？因为缺少 topology knowledge 和 precondition knowledge

**§2 Background：三层知识框架**
- L1 Schema / L2 Topology / L3 Precondition
- 用 M-005 和 M-008 的具体例子说明每一层

**§3 128 Bug 的量化分析**
- Bug 分类：category × parallel_dimension × invariant_type
- required_trace_fields 频率分析 → 最优 schema 设计
- 侵入性 vs 覆盖率 trade-off

**§4 方法：如何获取 L2 和 L3 知识**
- LLM 从源码提取 topology-aware parameter classification
- LLM 从多源信息提取 precondition
- Structured JSON spec → SQL 编译

**§5 实验**
- 真实 Megatron 复现结果
- 有 semantic knowledge vs 没有的检测率对比
- 和 TrainCheck / TTrace 的对比

**§6 Benchmark 发布**
- 128 bug dataset + sdctrace 工具 + invariant 库

## 4. 和审稿人预期的对话

**Q: "你就是在 training trace 上跑了个 pattern matching，有什么新的？"**
A: 不是。我们发现 pattern matching 只能覆盖 20% 的 bug。核心贡献是揭示了"为什么不够"以及"还需要什么知识"。

**Q: "TrainCheck 也做了类似的事，你和它有什么区别？"**
A: TrainCheck 的 trace pattern 不区分"TP shard 导致的正常差异"和"真正的 bug"。我们的实验在 M-005 上直接验证了这一点——INV-001 在 fixed 版本上有 57 个 FP。解决这个问题需要 topology knowledge，这是 TrainCheck 不具备的。

**Q: "你怎么证明 LLM 能提取你说的这些知识？"**
A: 我们用 LLM 分析 Megatron 源码生成了"TP 下哪些参数应该一致"的列表。与人工分析对比，precision=X%, recall=X%。关键是：人工分析需要理解整个 Megatron 的并行架构（数百个文件），LLM 可以在几分钟内完成。

**Q: "128 个 bug 够吗？"**
A: 这是目前最大的分布式训练 silent error 数据集。之前的工作（TrainCheck 用 15 个，TTrace 用 8 个）远少于此。更重要的是，我们不是简单列举 bug，而是对每个 bug 做了结构化分析（category、parallel_dimension、required_trace_fields、detection_signal），这使得量化分析成为可能。

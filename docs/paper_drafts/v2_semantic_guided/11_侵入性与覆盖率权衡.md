# 侵入性与覆盖率的权衡

> 核心发现：trace 方案的简单性和迁移性与 bug 覆盖率之间存在 trade-off。
> 这里记录不同侵入层级能覆盖的 bug 类型和数量，后续可画实验图。

---

## 1. 侵入性层级定义

| 层级 | 侵入方式 | 改动量 | 迁移成本 |
|------|---------|--------|---------|
| **L0 零侵入** | 只用 PyTorch 原生 hook（optimizer pre/post step） | 2 行代码 | 换框架/版本零成本 |
| **L1 轻侵入** | L0 + 在 forward hook 中记录统计量（norm/mean/std） | 5-10 行 | 几乎零成本 |
| **L2 中侵入** | L1 + 注册 per-layer forward hook 采集 activation | 20-30 行 | 每个框架需要适配 layer 结构 |
| **L3 框架侵入** | L2 + 读取框架内部状态（micro_step_id, loss_scale, grad buffer） | 50-100 行 | 每个框架版本需要单独适配 |
| **L4 深度侵入** | L3 + hook NCCL 通信层 / 修改训练循环 | 200+ 行 | 和框架强耦合，迁移成本高 |

---

## 2. 每个层级能采集的数据

### L0：零侵入（当前 auto_trace 方案）

采集点：optimizer.step 前后 + tracer.step()

| 数据 | 采集方式 | GPU→CPU 拷贝？ |
|------|---------|---------------|
| param cksum | `hash(param.data.cpu())` | 是（开销大） |
| param shape/dtype | `param.shape`, `param.dtype` | 否 |
| has_nan/has_inf | `param.isnan().any()` | 否（GPU 上算） |
| grad cksum | `hash(param.grad.cpu())` | 是 |
| optimizer state cksum | `hash(state['exp_avg'].cpu())` | 是 |
| loss value | `loss.item()` | 极小 |
| learning rate | `optimizer.param_groups[0]['lr']` | 否 |
| RNG state cksum | `hash(torch.cuda.get_rng_state())` | 极小 |

### L1：+统计量（无额外侵入，只是多算几个值）

在 L0 基础上增加：

| 数据 | 采集方式 | GPU→CPU 拷贝？ |
|------|---------|---------------|
| param norm | `param.data.norm().item()` | 否（GPU 上算，只传 1 个标量） |
| param mean | `param.data.mean().item()` | 否 |
| grad norm | `param.grad.norm().item()` | 否 |
| grad mean | `param.grad.mean().item()` | 否 |

关键优势：**norm/mean 不需要 GPU→CPU 拷贝**，开销远小于 hash。

### L2：+activation hook

在 L1 基础上增加：

| 数据 | 采集方式 | 需要什么 |
|------|---------|---------|
| attention output cksum | `model.attn.register_forward_hook()` | 知道 attention 层的名字 |
| MLP output cksum | `model.mlp.register_forward_hook()` | 知道 MLP 层的名字 |
| residual stream cksum | hook residual add | 需要了解模型结构 |

迁移成本：每个框架的模型结构不同，layer 命名不同，需要适配。

### L3：+框架内部状态

在 L2 基础上增加：

| 数据 | 采集方式 | 框架相关性 |
|------|---------|-----------|
| micro_step_id | 从训练循环中读取 | Megatron 和 DeepSpeed 存储方式不同 |
| loss_scale | 从 optimizer/scaler 读取 | 混合精度框架各不同 |
| gradient accumulation buffer | 从框架内部 buffer 读取 | 每个框架实现不同 |
| communication group info | 从 parallel_state 读取 | 框架高度相关 |

### L4：+通信层 hook

在 L3 基础上增加：

| 数据 | 采集方式 | 侵入程度 |
|------|---------|---------|
| all-reduce 输入/输出 | monkey-patch `torch.distributed.all_reduce` | 全局修改 |
| 通信 group membership | 拦截 process group 创建 | 需要在初始化前 hook |
| 通信时序 | NCCL trace / CUPTI | 需要环境变量或编译选项 |

## 3. 每个层级能覆盖的 bug 数量（基于 128 个 bug 分析）

| 层级 | 能检测的 bug 类型 | 预估覆盖 bug 数 | 覆盖率 | 增量 |
|------|-----------------|---------------|--------|------|
| **L0** | cross-rank equality (cksum), dtype/shape mismatch, NaN/Inf | ~25 | ~20% | — |
| **L1** | L0 + bounded_change (norm/mean 异常), 参数不更新, LR 异常 | ~65 | ~50% | **+30%** |
| **L2** | L1 + attention 逻辑错误, activation 异常 | ~80 | ~63% | +13% |
| **L3** | L2 + gradient accumulation 时序, loss_scale 错误, micro_step bug | ~100 | ~78% | +15% |
| **L4** | L3 + 通信 group 错误, 通信时序 bug | ~115 | ~90% | +12% |

### 不可覆盖的 bug（~13 个，~10%）

无论侵入到什么程度都检测不了：
- Sub-percent 数值偏差（所有 rank 相同的微小错误，需要 reference implementation）
- 数据加载逻辑错误（需要追踪 dataloader 内部状态）
- 某些 checkpoint 文件级 corruption（需要对比文件内容）

## 4. 开销估算

假设 1B 参数模型，8 GPU：

| 层级 | 主要开销来源 | 估算开销 |
|------|-----------|---------|
| **L0** | GPU→CPU hash 拷贝（每 step 每 rank ~1000 个 tensor） | ~5-10% |
| **L1** | GPU 上计算 norm/mean（无拷贝） | ~1-2% |
| **L2** | L1 + activation hash（额外 ~100 个 tensor） | ~2-3% |
| **L3** | L2 + 读取框架状态（极小） | ~2-3% |
| **L4** | L3 + 通信 hook（每次通信额外开销） | ~5-8% |

注意：**L1 的开销反而比 L0 低**！因为 L1 用 norm/mean（GPU 上算，传标量）替代部分 hash（GPU→CPU 全量拷贝）。

## 6. 论文价值

这个权衡分析本身就是一个 contribution：

> 没有人系统地量化过"trace 侵入程度"和"silent error 检测覆盖率"之间的关系。我们基于 128 个真实 bug 的分析表明，从零侵入（20%）到轻侵入（50%）的跃升最大且开销最低，这为实际部署提供了明确的工程指导。

这也回答了 reviewer 的一个必然问题："你的方法需要改多少框架代码？"——答案是分层的，用户可以根据自己的需求选择侵入层级。

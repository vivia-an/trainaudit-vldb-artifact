# 关键问题与风险

---

## 1. 方案整体风险评估

| 风险 | 严重性 | 可控性 | 说明 |
|------|--------|--------|------|
| Healthy trace 本身含 bug | 高 | 中 | Bootstrapping 问题：用"可能有问题的数据"做 ground truth |
| Predicate template 不完备 | 高 | 高 | 模板库可以持续扩展，且可以对照 benchmark 验证 |
| LLM hypothesis 覆盖不全 | 中 | 高 | 多次采样 + gap analysis 可缓解 |

## 2. 最关键的问题逐个分析

### 2.1 Bootstrapping 问题："Healthy" 怎么保证？

**问题**：如果 healthy trace 本身含有一个未发现的 silent error，从中学到的 invariant 就会把错误状态当作正常。

**缓解策略**：
1. **多版本交叉验证**：用框架的多个版本跑 trace——如果某个 invariant 在 v1 成立但 v2 不成立，需要调查
2. **Single-GPU reference**：对关键 step，跑一个 single-GPU 版本作为 ground truth 参照
3. **数学性质锚点**：某些 invariant 有数学保证（如 all-reduce 后梯度应该相同），不需要从数据学习
4. **渐进信任**：初始库只包含高置信度 invariant；随着运行积累更多 healthy trace，逐步扩展

这个问题无法完全消除，但可以在论文中显式讨论作为 limitation。

### 2.2 和 TrainCheck 的本质区别怎么论证

**Reviewer 可能的质疑**："你的方法不就是用 LLM 缩小搜索空间后再做 TrainCheck 吗？"

**回应**：

核心区别不在于"有没有 LLM"，而在于**能检测什么类型的 bug**：

| Bug 类型 | TrainCheck 能否检测 | 新方案能否检测 | 为什么 |
|----------|-------------------|--------------|--------|
| API 调用顺序异常 | ✅ | ❌（不看 API trace） | TrainCheck 的强项 |
| DP 参数不一致 | ❌（不看 tensor 值） | ✅ | 需要 cross-rank tensor checksum 比较 |
| Gradient accumulation 时序错误 | ❌ | ✅ | 需要 micro_step 级 trace + 跨 stage 比较 |
| Optimizer state 不同步 | ❌ | ✅ | 需要 topology-aware cross-rank 检查 |
| 通信组配置错误 | 部分 | ✅ | TrainCheck 只看调用是否发生，不看结果是否正确 |

**关键论证**：TrainCheck 的 trace 是 API-level（"谁调用了什么"），我们的 trace 是 state-level（"调用后状态是什么"）。**检测能力由 trace 的语义层级决定，不只是搜索算法。**

加上 LLM 的语义引导使得搜索有方向性，不会产生 TrainCheck 那样的 spurious pattern。

### 2.3 Predicate Template 的完备性

**问题**：如果一个 bug 需要的检查不在 template 库中，系统就检测不了。

**验证方法**：对照 B1-B15 的 15 个真实 bug，逐个分析：
- 每个 bug 需要什么类型的检查？
- 当前 template 库能覆盖吗？
- 如果不能，需要添加什么 template？

**预期结果**：大部分 bug 属于以下几类：
- Cross-rank equality violation（DP/TP 不一致）
- Cross-step temporal violation（counter/buffer 时序错误）
- Cross-stage state violation（某 stage 前后状态不符合预期）

如果 template 库覆盖这三大类，应该能检测 B1-B15 中的绝大部分。

### 2.4 Contribution 够不够一篇顶会？

**Paper 的 contribution 结构**：

1. **Problem formulation**：提出 "semantic-guided predicate discovery" 范式，把 SE 领域的 "LLM + formal tool" 混合范式适配到 distributed training
2. **Method**：四层 pipeline（hypothesis → enumeration → validation → filtering），每层都有具体的技术设计
3. **Insight**：从多配置 healthy trace 自动发现 precondition（而非让 LLM 猜），是一个 clean 的技术贡献
4. **Evaluation**：在 33+15 个 bug 上 vs TrainCheck / TTrace 对比

**可能不够的地方**：
- 如果 predicate template 太简单（只是 COUNT DISTINCT + GROUP BY），reviewer 可能觉得技术深度不足
- 需要在实验中证明 LLM 的 semantic guidance 确实带来了显著的覆盖率提升（vs 无引导的枚举）

## 3. 需要尽早验证的实验

| 实验 | 目的 | 预期时间 |
|------|------|---------|
| 对照 B1-B15 验证 template 覆盖率 | 确认方案的上限 | 1-2 天 |
| 跑 2-3 种配置的 healthy trace | 验证 precondition 自动发现是否 work | 3-5 天 |
| 对比 "有 LLM 引导" vs "无引导全枚举" | 证明 semantic guidance 的价值 | 1 周 |
| 注入一个已知 bug 验证 end-to-end 检测 | 验证 pipeline 端到端可行 | 2-3 天 |

建议优先做第一个（对照 B1-B15 验证 template 覆盖率），如果 template 覆盖率不足，整个方案的天花板就确定了。

## 4. 和当前 TrainAudit v1 的关系

两种策略：

**策略 A：完全替换**
- 用新方案替换 v1 的 invariant mining pipeline
- 保留 data collector 和 runtime verifier 的基本架构
- 论文重写

**策略 B：作为 v1 的改进**
- 在 v1 的框架内引入新方案作为一个 alternative invariant discovery method
- 对比 v1（纯 LLM mining）和新方案（semantic-guided discovery）
- 论文增量修改

**建议**：先做策略 B 的对比实验。如果新方案显著优于 v1，再决定是否策略 A。

## Abstract（重写思路）

**老版本**：以 "we present TrainAudit" 开篇，叙述 motivation 弱。

**新版本结构**（约 200 词）：
1. **第 1 句（钩子，故事 B）**：过去十年训练 observability 都在问"是否健康"，问错了问题。
2. **第 2–3 句（故事 A 引入）**：silent error 的信息一直在数据里，缺的是规则。我们把"AI 可挖出的规则远多于人类可维护"命名为 rule deficit，并指出现有方法（loss、TrainCheck、TTrace、TrainVerify）都是 rule deficit 下的妥协。
3. **第 4–5 句（TrainAudit 是新范式实例）**：TrainAudit 是第一个直面 rule deficit 的系统：多 agent LLM pipeline 直接读源码挖 invariant，对抗式过滤把幻觉当结构性风险，SQL verifier 在 runtime 做关系性检查。
4. **第 6 句（数字，但不是主角）**：在 33 个注入 fault + 15 个真实 bug 上检测率 90.9%、运行时开销 ~5%、clean run FPR 0%。
5. **第 7 句（区分定位）**：与 TrainCheck 等方法 *互补*，覆盖 behavioral templates 在表达力上结构性不可达的 fault class。

**关键措辞替换**：
- "we propose a system" → "we present the first system to directly attack the rule deficit"
- "qualitatively different methodology" → "complementary methodology that lifts a long-standing bottleneck"
- "outperforms TrainCheck" → "covers a fault class structurally outside TrainCheck's expressive scope"

## §1 Introduction（重写大纲）

### 段 1：信息一直都在 + Rule Deficit 概念引入（故事 A 第 1 段）
- 一句话：每一个 silent error 在出现的瞬间都在某个中间状态里留下痕迹。
- 第二句：缺的不是数据，是规则。
- 给出第一个硬数据：Megatron-LM 全仓库与训练状态相关的 assert 数 N₁ vs TrainAudit 挖出的 249，比例 X 倍——**这就是 rule deficit**。
- Figure 1 仍然用 micro_step_id 例子，但 caption 换成强调"信号一直都在 micro_step_id 这个变量里——只是没人写规则去看它"。

### 段 2：现有方法都是 rule deficit 下的妥协（故事 A 第 2 段）
- loss/grad norm：不写规则，只看标量
- TrainCheck：从 trace 推规则，受模板表达力限制
- TTrace：用 reference 代替规则
- TrainVerify：把规则形式化成 plan 等价性
- 共性：都在绕开规则供给瓶颈，没人直面它

### 段 3：AI 改写规则供给侧的 economics（故事 A 第 3 段）
- AI 之前：spec 成本随系统复杂度爆炸
- AI 之后：spec 成本曲线第一次和复杂度脱钩
- 给出第二个硬数据：每条 invariant 的 AI 成本 \$0.43 vs 人类专家成本估算 \$20–50，约 50–100 倍差距

### 段 4：TrainAudit 是这个新范式的第一个完整 instantiation
- 不只是"用 LLM 挖规则"——回答的是"AI 充当规则供给方之后整个 pipeline 应该长什么样"
- 三个组件不是工程 patch 而是新范式的必然结构：
    - Bidirectional Verification（幻觉是结构性风险）
    - Topology-Aware Pruning（规则丰度的副作用）
    - SQL Verifier（百级千级规则只能用关系代数批量检查）

### 段 5：Contributions
- **Contribution 1（概念）**：识别并形式化 rule deficit；提出 intent-anchored invariant 概念
- **Contribution 2（系统）**：第一个直面 rule deficit 的完整 pipeline，含 bidirectional verification、topology pruning、SQL verifier
- **Contribution 3（实证）**：33 注入 + 15 真实 bug，90.9% 检测率，5% overhead，0% FPR
- **Contribution 4（互补性证据）**：249 条挖出的 invariant 中 X% 落在 TrainCheck 5 个 template 表达力之外，构成"complementary fault class"的硬证据

- 保留现有的 $f_{ideal}$ vs $f_{actual}$ 形式化

- **修排版**：Eq. (3) 用 `\text{Valid}` `\text{Error}`

- **加一个 Proposition**（核心论点 01 提到的那个）：

> **Proposition 1（Behavioral templates 的表达力上界）**.
> 设 $\mathcal{T}$ 是仅以 API 调用序列为输入的 invariant template 集合。存在一对执行 $e_1, e_2$ 满足 $\text{trace}(e_1) = \text{trace}(e_2)$ 但 $\text{state}(e_1) \neq \text{state}(e_2)$，因此对任意 $t \in \mathcal{T}$ 有 $t(e_1) = t(e_2)$。
>
> **推论**：B2、B5、B6、B10 这类"API 序列正确但状态语义违反"的 fault 在 $\mathcal{T}$ 内结构性不可检测。

- 紧跟一个 B10 trace dump 的 side-by-side（正确 vs 错误的 API call sequence 完全相同）

### §2.3 Rule Deficit and the Authoring Bottleneck（**新增小节**）
- 给出 rule deficit 的工作定义：人类可维护的规则数 vs 系统设计意图蕴含的 invariant 数之间的长期缺口

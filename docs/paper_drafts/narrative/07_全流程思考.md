# 07 · 全流程思考：从数据多样性到 invariant，再到检验未知数据，再到延续

> **本文档是 narrative 系列里最接近 paper 实际内容的一篇。**
> **它解决的是：脱开"故事/positioning"层，把整个 pipeline 的工作机理讲清楚——这是新版 paper 真正应该讲的核心。**

## 起点：用户给出的两个端点

讨论的起点是用户提的两件事：

1. **数据端**："能 trace 的数据实在是太多了，数据的多样性决定了能挖掘出来信息的基础。"
2. **检验端**："针对一个我们不知道是对还是错的一份数据，要有一些挖出来的不变量去检测它。"

这两个端点中间夹着真正的难题：**invariant 怎么挖出来？怎么确定它可行？**

下面把整个 pipeline 走一遍，最后讨论它的延续方向。co

---

## Part 1：数据多样性的真正含义——它是 invariant 的*搜索空间*

Trace 数据不只是"多"，它是一个**高维笛卡尔积**：

$$\text{trace} \subseteq \text{step} \times \text{stage} \times \text{parameter} \times \text{rank}_{\text{(DP,TP,PP,CP,EP)}} \times \text{attribute}$$

具体维度：
- **step**：数千个
- **stage**：7 个（before-forward / after-forward / main-grad / after-backward / before-opt / after-opt / get-batch）
- **parameter**：数千个 named tensors
- **rank**：DP × TP × PP × CP × EP 的并行组合
- **attribute**：cksum / shape / type / quantile / 高阶矩 / grad_cksum / ...

### 关键洞察

这个 grid **就是 invariant 的语言**。每一条可能的 invariant，在数学上都是这个 grid 上的一个谓词（predicate）。Grid 越细、越正交，能表达的 invariant 就越多。

举一个具体的例子：

> "梯度跨 DP rank 一致"

这条规则要能被表达，trace schema 必须同时具备：
- `grad_cksum` 字段（attribute 维度）
- `dp` rank 字段（rank 维度）
- 至少能区分 `model-after-backward` 这个 stage（stage 维度）
- `parameter.name` 用于按参数分组（parameter 维度）

任何一个维度缺失，这条 invariant 数学上就不可表达——不管 LLM 多聪明都没用。

### Mining 的第一性原理

> **Data schema 是 invariant 的语言。扩 schema 才能扩 invariant 表达力。**

这个原理直接转化为 paper 的一个 contribution：**Data Collector 不是"工程支撑组件"，它是 invariant 表达力的 enabler**。当前 schema 已经足够支撑 249 条 invariant；如果加上 activation tensor、跨节点通信日志，能解锁另一类 invariant。

这一点在现在的 paper 里完全没有讲清楚——Data Collector 章节只说了"我们采集了什么"，没说**为什么这些字段刚好是 invariant 表达力的最小完备集**。

## Part 2：Mining——把"social knowledge"翻译成"grid 上的谓词"

真正的 mining 流程不是"LLM 提 invariant"，是**完成一次跨知识源的翻译**。这次翻译必须穿过 7 个关卡。

### 关卡 1：Gap-aware hypothesis generation（避免 LLM 漫无目的）

不能让 LLM 自由发挥。必须给它一个**结构化的搜索 frontier**：

> 现有 library 已经覆盖了 grid 的哪些格子？哪些 (stage × parameter class × rank pattern × attribute) 组合还是空的？

让 LLM 针对未覆盖的格子提 hypothesis。这把"什么样的 invariant 值得提"从主观判断变成**结构化覆盖问题**。

### 关卡 2：Evidence grounding（必须假设 LLM 会编引用）

对一条 hypothesis，要求至少 2 个**独立**的支撑源。每个源必须给：
- `file_path:line_number`（可机器验证）
- 论文 URL + version + 引文段落
- Issue/PR 编号 + 具体讨论内容

这一步的真正工作量不在"找证据"——LLM 总能编出证据——而在**让证据可机械核验**，从而把 LLM 的不可靠 citation 过滤掉。

**5-layer verification 不是设计优雅，是因为 LLM citation 不可信、必须有独立的事实校验机制。**

### 关卡 3：Schema binding（这是 paper 真正核心，也是当前最被低估的一步）

这一步把"自然语言软概念"翻译成"grid 上的硬约束"，是整个 pipeline 里最难、最被外人忽视的一步。

举例：LLM 提出

> "DP optimizer states should be consistent across ranks"

这句话在数学上**完全不可执行**，必须绑定到 schema：

| 软概念 | 硬绑定 |
|---|---|
| "DP" | `same_pp_rank AND same_tp_rank AND different_dp_rank` |
| "optimizer states" | `parameter.name LIKE '%.exp_avg' OR LIKE '%.exp_avg_sq'` |
| "consistent" | `COUNT(DISTINCT cksum) = 1` |
| 时机 | `stage = 'model-after-optimizer-step'` |

绑定之后这条 invariant 才有意义、才能跑 SQL、才能检验未知数据。

> **没有 schema binding 的 invariant 是文学，不是工程。**

这一步的难度被现在的 paper 严重低估了。它实际上是 **"自然语言知识 → 关系代数谓词" 的语义映射**。每条 invariant 都需要这次翻译，且翻译有错就全错。

**改写建议**：在 §3.2 单独开一小节叫 "Schema Binding"，放在 Bidirectional Verification 之前。这是 paper 厚度提升的最大单一抓手。

### 关卡 4：Counterexample-driven precondition tightening

LLM 提出的 invariant body 通常是对的，但**适用边界（precondition）几乎总是错或缺**。

例子：
- LLM body：「DP optimizer states should be consistent.」
- 反例 1：「ZeRO-3 怎么办？」→ ZeRO-3 是 sharded，invariant 不成立
- 反例 2：「distributed optimizer with CPU offload？」→ 时序更复杂
- 反例 3：「frozen weights？」→ 没有 optimizer state

每个反例迫使 LLM 收紧 precondition：

```json
"applicable_conditions": {
  "dp": "> 1",
  "zero_stage": "< 3",
  "cpu_offload": "false",
  "param.requires_grad": "true",
  "stage": "= 'model-after-optimizer-step'"
}
```

### Social distribution 的真正形态在这一步暴露

- **body** 来自 ZeRO 论文的算法描述
- **precondition** 散落在：ZeRO-3 论文、CPU offload 的 PR 讨论、distributed optimizer 的 commit message、frozen weight 实现的 issue 里

**这些来源永远不在同一个文档里。**

这就是为什么 social knowledge synthesis 是必要的：

> **body 容易找，precondition 找不全。而正是 precondition 决定了 invariant 的真正可用性。**

### 关卡 5：Confidence threshold（承认没有 oracle）

经过反例还活着的 invariant 还要打分：

$$\text{Conf}(c) = \alpha \cdot \frac{|\mathcal{E}^+|}{|\mathcal{E}^+|+|\mathcal{E}^-|} + (1-\alpha) \cdot \frac{|\mathcal{CE}_r|}{|\mathcal{CE}|}$$

低于 0.8 阈值的丢弃。

这不是工程妥协——是**承认 social knowledge 不存在 absolute oracle 这个 epistemic 事实**。0.8 阈值意味着我们决定"在哪个置信水平上把社会综合判断当作工作真相"。

### 关卡 6：SQL 编译（暴露隐藏精度问题）

绑定 + precondition 完整的 invariant 能编译成 SQL。但编译时会暴露之前没注意的问题：

- Trace 里这个参数有些 step 没采到 → NULL 怎么处理？
- `DISTINCT cksum` 如果只有 1 条记录，统计上不显著
- 时序条件需要用 window function 还是 self-join？

每条 invariant 在 SQL 编译时都可能 fail，需要 fallback parsing 或者 reject。

### 关卡 7：Library consistency

新加的 invariant 跟已有的有没有重复、矛盾？需要做 semantic equivalence check（关卡 1 已经做过一次粗的；这一步是细的）。

### 7 关卡的"漏斗 yield"是 paper 应该有的硬数据

| 阶段 | 候选数 | 杀的原因 |
|---|---|---|
| LLM raw proposal | ~?? | — |
| 去重（vs library） | | 复述 |
| Evidence sufficiency（≥2 sources） | | 撑不出 2 个独立来源 |
| Counterexample refutation | | 反例下崩 |
| Confidence ≥ 0.8 | **249** | 信心不足 |
| SQL 编译通过 | | 编译失败 |
| Library consistency | | 与已有冲突 |

**这张表才是真正应该震慑读者的东西**——它直接证明 mining 的工作量在"杀"不在"生成"，每一层的杀都对应一种社会分布性的副作用。这是**架构必要性的硬证据**。

## Part 3：用挖出来的 invariant 检验"未知对错"的数据

现在有 249 条编译好的 invariant，给一份新 trace（不知道有没有 silent error），怎么检验？

### Step A：Topology-aware pruning

解析启动脚本，知道当前 run 的 (DP, TP, PP, ...)。从 249 条里筛出**适用子集**——TP=1 的 run 上，所有 TP-only invariant 全部去掉。这一步直接砍掉 30-40%（实测 35%）。

### Step B：层级化执行（粗 → 细）

不要一上来跑所有 invariant。先跑 root-level coarse check：

> "DP ranks 之间 final state 是否大致一致？"

- 通过 → 整个子树跳过
- 违反 → 才下钻到 fine-grained：
    - "具体哪个参数 inconsistent？"
    - "在哪个 step？"
    - "checksum 差距是 1 个 distinct value 还是多个？"

这是为了控制开销——百级千级 invariant 全跑会爆，drill-down 让 95% 时间只花在 5% 真正可疑的子树上。

### Step C：Violation 分类

SQL 跑完得到 violation records。但**不是每个 violation 都是真 bug**：

| 类别 | 描述 | 占比预期 |
|---|---|---|
| True bug | cksum mismatch 真的来自代码错误 | 少数（1-5%）|
| NULL artifact | 某些 step 没采到这个参数 | 中等 |
| Corner case | invariant 的 precondition 没覆盖到这个特殊 config | 中等 |
| Topology mismatch | 被 pruning 漏掉的不适用 invariant | 小 |

需要 Analysis Agent 二次判断每个 violation 属于哪一类。这一步本质上是**回到 social knowledge synthesis**——判断"这个 violation 是否真的违反了我们想检测的语义"。

### Step D：Localization chain

真 violation 触发诊断报告。结构化输出：

```
Symptom: Optimizer state inconsistency across DP ranks
  └─ Trigger: distinct_cksum_count=2 for final_layernorm.bias
      └─ Affected ranks: dp=0 vs dp=1
          └─ At step: 142, stage: model-after-optimizer-step
              └─ Likely root cause: missing all-reduce in optimizer step
```

这不是简单"哪里错了"，而是**重建 silent error 的传播链**——从 high-level 语义违反一直到具体 record。

## Part 4：这套流程的"延续"——它指向什么

如果接受上面这套流程，那 TrainAudit 自然指向五个方向的延续。这些延续不只是 future work，更重要的是它们**让 paper 的命题超出 LLM training 这个 instance**，落到方法论本身。

### 延续 1：Self-evolving invariant library（最近的下一步）

现在 library 是"一次挖、永久用"。但实际跑训练每次都暴露：

- **False positive** → invariant 的 precondition 不够紧 → 自动收紧
- **False negative** → grid 上某个格子还没覆盖 → 自动补 mining
- **新版本框架** → 部分 invariant 失效 → 自动 invalidate + remine

把这个反馈环建起来，library 就从静态变成**在线演化**——这本身就是一篇 follow-up paper。

### 延续 2：Cross-framework transfer 的形式化

Megatron 挖的 249 条，多少能用到 DeepSpeed？答案的结构是：

| 知识来源类型 | 可迁移性 |
|---|---|
| Framework-agnostic（ZeRO 论文、numerical stability 公认结论） | 直接迁 |
| Framework-specific（Megatron 的 distrib_optimizer 私有 API） | 不可迁 |
| 概念相同实现不同（两框架的 ZeRO-3） | 需要 re-binding |

这是 social knowledge 在框架之间的**可迁移性图谱**——能形式化的话是另一个 contribution。

当前 §4.4 (Generalizability) 用"42% / 30%"这种数字来表达这件事，太粗了。真正的 contribution 应该是**给出可迁移性的结构化分类**。

### 延续 3：从 detect 走向 self-heal（最有争议）

很多 invariant 暗含 fix：

- "Frozen weight gradients should be all-reduced" → 检测到没 reduce，**直接补一次 all-reduce**
- "Counter should reset at step boundary" → 检测到不一致，**强制 reset**

这是 self-healing distributed training 的方向。但要小心——错误的 auto-repair 可能比 silent error 更危险。需要置信度极高 + 反例 saturation 的 invariant 才能授权 auto-repair。值得做但要谨慎。

### 延续 4：跨领域复用——这个 architecture 不只属于 LLM training

整个 pipeline（trace schema → social knowledge mining → counterexample-validated invariants → SQL on relational state）是 **distributed system 通用的 silent error 检测 architecture**：

| 领域 | trace schema | social knowledge sources |
|---|---|---|
| 分布式数据库 | replica state, txn log | ACID 论文、Paxos/Raft 论文、源码 |
| 分布式文件系统 | inode, replica, lease | GFS 论文、HDFS 文档、commit history |
| 共识协议 | term, log index, vote state | Raft 论文、TLA+ spec、issue tracker |
| 微服务 | span, request id, txn state | OpenTelemetry spec、领域文档 |

每个领域都符合"social knowledge → operational invariant"的模式。

> **TrainAudit 是这套 architecture 在 LLM training 这个 instance 上的第一次完整 instantiation——但 architecture 本身比 instance 重要得多。**

这一句话能写到 §6 Conclusion 里，把 paper 的 reach 扩出 ML 领域，进入更宽的 systems 社区。

### 延续 5：随 base model 能力 scaling

每条 invariant 的成本 \$0.43 是 GPT-4.1 价格。GPT-5 / Claude Opus 5 / 未来 reasoning model 时代：

- 同样的 mining 能挖出**更多、更精确**的 invariant
- 单条成本**下降**
- Schema binding 准确率**提高**

这意味着：

> **TrainAudit 的覆盖率是 base model 能力的单调函数——每次 base model 升级，library 就自动扩。**

这是一个 **scaling claim**：我们的方法 *inherits the LLM scaling curve*。这是大多数传统系统工作没有的性质——SQL 数据库再好也不会随 LLM 升级而变更好；TrainAudit 会。

## 总结：把整个流程映射回 paper structure

| 流程阶段 | 对应 paper 章节 | 应该突出什么 |
|---|---|---|
| Part 1 (data 多样性) | §3.3 Data Collector | schema 是 invariant 的语言；不是工程支撑而是 enabler |
| Part 2 关卡 1-2 | §3.2 Invariant Miner 前半 | gap-aware hypothesis + citation distrust |
| **Part 2 关卡 3** | **目前 paper 严重缺失，必须新增小节** | schema binding 是真正最难的一步 |
| Part 2 关卡 4 | §3.2 Bidirectional Verification | precondition 的 social distribution |
| Part 2 关卡 5-6 | §3.2 末段 + Appendix | confidence calibration as epistemic stance |
| **Part 2 漏斗 yield 表** | **目前 paper 缺失** | 真正震慑读者的硬数据 |
| Part 3 | §3.4 Verifier | hierarchical + drill-down + violation classification |
| **Part 4 延续** | **目前 paper 缺失（无 §6）** | 把命题超出 LLM training |

## 当前 paper 的两个最大缺失

### 缺失 1：Schema binding 没有被讲清楚

它现在被淡化成了"compile to SQL"，但实际上是 **"自然语言知识 → 关系代数谓词"的语义映射**。每条 invariant 的可用性都取决于这次翻译——这是 paper 厚度可以显著提升的最大单一抓手。

### 缺失 2：延续部分基本没写

一个 ICML 论文如果不讲 implication，读者读完就丢了。延续的 5 个方向给 paper 提供了在 LLM training 之外的持续讨论空间——尤其是延续 4（cross-domain）和延续 5（inherit LLM scaling），这两个都是大多数同类工作没有的性质。

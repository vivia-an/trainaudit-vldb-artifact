# 02 · 故事 A：规则赤字（Rule Deficit）

> **主推叙事，作为论文骨架。**

## 故事的核心 motif

LLM 训练的 silent error 检测领域有一个长期被忽视的事实：**信息从来都在数据里——参数 checksum、optimizer 内部状态、micro_step_id 计数器、TP 组的梯度——这些信号一直存在。问题从来不是"看不见"，而是"不知道该用什么规则去看"。**

而"规则"这件事的成本，几十年来都是被人类专家锁死的：

- 一个专家可以为框架手写几十条 assert；
- 一个团队可以维护一两百条；
- 但 Megatron-LM 这种规模框架的设计意图里，至少蕴含数千条可以验证的 invariant。

我们把这种 **AI-extractable rules \>\> human-maintained rules** 的长期缺口，命名为 **Rule Deficit（规则赤字）**。

**所有现有的 silent error 检测方法，本质上都是在 rule deficit 这个约束下找不同的妥协**——而不是直接攻克它。

## 重新解读现有工作（这是 §5 重写的关键）

| 系统 | 在 rule deficit 下做了什么妥协 | 代价 |
|---|---|---|
| Loss / grad norm / NaN check | 不写规则，只看最粗的 aggregate 信号 | 检测晚、信息少 |
| TrainCheck | 用模板从 trace 里**统计**出规则 | 只能看见 trace 里能看见的；模板表达力有限 |
| TTrace | 用 reference 单卡执行**代替**规则 | 必须付得起 reference 的代价；不能跨 topology |
| TrainVerify | 把规则**形式化**成 plan 等价性 | 只能在执行前做静态证明；in-flight 不可用 |
| 手写 assert | 直接写规则，但只写得动几十条 | 覆盖率低，且容易和代码演化脱节 |

**洞察：每条妥协都是在绕开"规则供给侧"这件事，而不是解决它。**

## 为什么现在能直面瓶颈：AI 改写了规则供给侧的 economics

这一段是论文的"时代感"所在，必须明确：

- **AI 之前**：规则的成本是一个专家一个 invariant 几十分钟到几小时的级别。这个成本曲线和系统复杂度同步增长——系统越复杂，每条 invariant 越难写。
- **AI 之后**：一个 capable 的 code-LLM 能在几分钟内读完一个 module 的源码、定位设计意图、产出一条候选 invariant。成本曲线第一次和系统复杂度**脱钩**。
- **关键不只是便宜了**：而是**规则供给从离散稀缺资源变成可连续按需生产的工作流**。这是一个 qualitative shift。

## TrainAudit 是这个范式的第一个完整 instantiation

这里要明确两个事：

1. **不只是"用 LLM 挖 invariant"**——任何团队都可以让 LLM 跑一遍源码然后输出一些规则。我们的工作回答的是 **"在 AI 充当规则供给方之后，整个 detection pipeline 应该长什么样"** 这个系统级问题。

2. **几个组件因此不再是 patch，而是这个新范式的必然结构：**
    - **Bidirectional Verification**：因为规则供给是 LLM，幻觉是结构性风险，所以 adversarial filtering 是 first-class，不是 ad-hoc safeguard。
    - **Topology-Aware Pruning**：因为 AI 挖出的规则覆盖各种并行配置，运行时必须按 topology 裁剪；这是规则丰度的副作用。
    - **SQL-based Verifier**：因为规则数量足够多（百级到千级），只能用关系代数批量检查；assert 这种点状机制不再适用。

把这三个组件 reframe 成"AI 时代 invariant detection pipeline 的必然结构"，立刻让它们从工程细节升级成方法论。

## Introduction 三段式样板（按故事 A 重写）

### 第 1 段：信息一直在，缺的是规则

> Every silent error in distributed LLM training already manifests in the data. A drifted checksum, a counter that did not reset, an optimizer buffer that was not synchronized—the signal is there, in some intermediate state, at the moment the fault occurs. What has been scarce, for as long as distributed training has existed, is the *rule*: the precise statement of what should hold among those signals, and where. We call this gap the **rule deficit**.

### 第 2 段：现有方法都是 rule deficit 下的妥协

> Every existing approach to silent error detection can be re-read as a different way of working *around* the rule deficit, rather than closing it. Loss curves and gradient norms avoid rules altogether by collapsing the state into a scalar. TrainCheck infers rules from execution traces, but only those expressible by its five behavioral templates. TTrace substitutes a single-device reference for explicit rules, paying the cost of a parallel oracle execution. TrainVerify formalizes rules as static plan equivalence, but cannot run in flight. Hand-written assertions express rules directly but cap out at the few dozens a team can maintain. None of these approaches has attempted to lift the deficit itself.

### 第 3 段：AI 改写规则供给侧 → TrainAudit

> The recent maturation of code-comprehending LLMs is the first development in three decades that changes the economics of rule authoring. A capable LLM can read every line of a framework's source, every paragraph of its documentation, every comment of its issue tracker, and propose a candidate invariant—at a per-rule cost three orders of magnitude below human authoring. The rule deficit ceases to be a fundamental constraint and becomes a workload. This paper presents **TrainAudit**, the first system designed from the ground up around this shift: a multi-agent LLM pipeline that mines invariants directly from framework source code, an adversarial filtering stage that treats hallucination as a structural risk rather than an afterthought, and a SQL-based runtime verifier that scales to the rule densities AI authoring makes possible.

## 这个故事如何吃掉审稿人最 nasty 的攻击

| 审稿人攻击 | 故事 A 的回应 |
|---|---|
| "你们就是用 LLM 替换了 trace mining" | 我们识别了 30 年的 rule deficit，并第一次直接攻击它，而不是绕开 |
| "TrainCheck 的 benchmark 你为什么不跑" | 我们的命题是 paradigm-level 的；TrainCheck 是 rule deficit 下的一个妥协方案，benchmark 比较是 instance-level 的次要问题 |
| "你们是不是 cherry-pick 了 fault" | rule deficit 的存在由 N₁ vs 249 的比值证明，与具体 fault 选择无关 |
| "Generalizability 数据弱" | rule deficit 的存在和"我们直面它"是 framework-agnostic 的论断；具体数字只是 instantiation |

## 风险与反驳预案

### 风险 1：审稿人觉得 "rule deficit" 是新名词、是 buzzword
**预案**：证据 1（grep 现有 assert 数量）必须放在 §1 第一个数字位置。"Megatron-LM 全仓库 53 条与训练状态相关的 assert，TrainAudit 挖出 249 条" 这种对比让概念立刻具象。

### 风险 2：审稿人觉得 "lift the deficit" 不止 LLM 可以做（比如 large-scale grep + 模板）
**预案**：在 §1 后接的位置说明 rule deficit 的两个子瓶颈是"读源码（语义理解）"和"形式化为可执行检查（表达能力）"——前者只有 LLM 能做、后者需要执行约束的多样化表达。简单的 grep + 规则模板做不到。

### 风险 3：审稿人觉得 "我们直面瓶颈" 这句话太大
**预案**：把 claim 收窄为 **"the first system to operationalize source-code-anchored invariant mining at production scale for distributed training"**。"第一次让 source code 直接作为 invariant 来源、并在生产规模下完整跑通" 是可防守的。

## 一段总结

这个故事把 paper 从"我们做了一个检测系统"升级成"我们识别并第一次解开了 silent error 检测领域的根本瓶颈"。它把 TrainCheck/TTrace/TrainVerify 都重新解读成"前史"，让 baseline 公平性争议在更高 abstraction 上被消解。它给三个工程组件（bidirectional verification、topology pruning、SQL verifier）一个范式级的解释而不是工程级的解释。它最后会把审稿人留下的印象浓缩成两个词："rule deficit" 和 "intent-anchored invariant"。
